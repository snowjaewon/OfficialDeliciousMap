## 판별 근거

판별 캐시가 `목사골농장`을 판단 보류(`음식점 여부 불분명`)로 둔 것은 상호의 `농장`만으로는 음식점인지
가를 수 없어서다. 실제로 네이버에는 같은 이름을 쓰는 나주의 농장(`나주목사골농장`, 나주시 금천면)도 있다.
이 이름이 광주에서 가리키는 곳이 식당임을 보이는 근거는 셋이다.

1. **인허가 자료.** [#73](issue-73.md)이 실제 키로 받아 둔 조회 캐시에서 질의 `목사골`의 결과를 읽었다
   (`geocode-lookup-v1.jsonl`, 키 앞 16자 `0729102df14ff8cd`). 일반음식점·휴게음식점·제과점영업 세 업종을
   전국에서 찾은 33건이다. 업종마다 한 쪽 100건에 못 미치므로 빠진 쪽이 없다. 사업장명이 정확히
   `목사골농장`인 업소는 **일반음식점** `전남광주통합특별시 서구 상무번영로 68, 1~2층 (치평동)` 하나다
   (관리번호 5810000-101-2014-00189).
2. **네이버 지역검색.** 질의 `목사골`의 캐시 결과(키 앞 16자 `ffa29210157e22aa`)가 `목사골농장`을 같은
   `서구 상무번영로 68 1, 2층`으로 준다.
3. **기관 공개자료.** #74와 같은 방법으로 받아 둔 시청 원본 251개를 모두 읽었다(대상 기간 밖 포함, 읽지
   못한 `.bin` 2개 제외). 표 칸 가운데 `목사골농장`을 공백 무시로 담은 칸을 모았다. 목적 칸
   (`간담`·`집행`·`추진`·`격려`·`회의`가 든 칸)과 40자를 넘는 칸은 뺐고, 칸이 모두 같은 행은 누적
   재게시로 보고 한 번만 셌다.

모든 표기가 한 상호를 가리키고, 다른 지점이나 다른 동네를 적은 표기는 없다. `목사골농장지점`은
도시공간국·창업진흥과·보도총괄팀 등 여러 부서가 적었고 인허가에는 그 이름의 별도 업소가 없다.
카드 가맹점명을 옮겨 적은 표기로 보인다. 행의 목적은 모두 간담회·직원 격려다. 카페와 함께 적은
행(`목사골농장/투썸플레이스` 등)은 식사 뒤 차를 마신 흐름으로 읽힌다.

판별 규칙·프롬프트는 바꾸지 않았다. 판단은 사람 보정(`data/manual/gwangju/classify.jsonl`)의 경로다.
판정은 에이전트가 적고 사람의 최종 확인은 이 PR 검토다.

## 지오코딩

### 새 조회

식당이 된 표기는 판단 보류였으므로 조회한 적이 없다. 네이버 지역검색에 새로 보낸 요청은 **5건**이다.
인허가 조회는 구성하지 않았다(`.env`에 `DATA_GO_KR_KEY`가 없다. #99와 같다).

| 조회 캐시 | 질의 | 키 앞 16자 | 후보 |
| --- | --- | --- | --- |
| 도시 `data/gwangju/` | `목사골농장` | `bb814ab608ab0834` | 3 |
| 도시 | `목사골농장 (서구 치평동)` | `bccb8c07d517e6ae` | 1 |
| 도시 | `목사골농장지점` | `20cecf831bcf01f4` | 0 |

| 서구 `orgs/gwangju-seo/` | `목사골농장지점` | `20cecf831bcf01f4` | 0 |

같은 질의의 두 조회는 캐시 줄이 바이트까지 같았다. 기관 캐시의 두 건은 기관 산출물을 다시 만들 때
쓰려고 받았다. 뒤에 그 산출물을 다시 만들지 않기로 해서([아래](#기관별-산출물은-다시-만들지-않았다))
지금은 어느 산출물도 읽지 않는다. 다음에 기관 산출물을 다시 만들 때 다시 묻지 않도록 캐시에 남겼다.

조회는 geocode 전에 geocode가 쓰는 함수(`lookup._reuse_or_search`)를 직접 불러 했다. 그래야 결과를 보고
업소 확인 줄을 쓴 뒤 geocode를 한 번만 돌릴 수 있다. 캐시 줄은 geocode가 조회했을 때와 같다. 요청은
허용한 세 질의만 내보내는 transport를 거쳤다. 목록 밖의 네이버 질의나 인허가·모델 요청은 예외로
끊었다(어댑터가 `unavailable`로 바꿔 캐시에 쌓지 못하도록 `BaseException`을 썼다). 뒤이은
`classify`·`geocode`·`closure`·`build`도 같은 transport로 돌렸고, 더 나간 요청은 없다.

## 실행과 결과

저장소 루트, Git Bash. 도시 전체 실행이다(CI가 도시 단위로 build한다). 모델 키(`GEMINI_*`)는 환경에서
뺐다. 커밋된 판별이 모델 없이 만든 것이고(#99), 판별 캐시에 없는 상호는 전처럼
`unclassified: model_not_configured`로 남아야 하기 때문이다. `--raw-root`는 #74와 같이 `fetch.json`이
기록한 경로다.

```text
uv run python -m deliciousmap classify --city gwangju --raw-root <fetch.json이 기록한 raw-root>
uv run python -m deliciousmap geocode  --city gwangju --raw-root <같은 값>
uv run python -m deliciousmap closure  --city gwangju --raw-root <같은 값>
uv run python -m deliciousmap build    --city gwangju --raw-root <같은 값>
```

위 명령을 `cli.main`에 [새 조회](#새-조회)의 transport를 넣어 실행했다.

| 단계 | 결과 |
| --- | --- |
| classify | 종료 0, 73초. 식당 6,834 → **6,899** · 판단 보류 2,279 → **2,214** · 비식당 607 그대로. 바뀐 레코드는 보정한 표기 65건뿐이다 |
| geocode | 종료 0, 159초. 결과 6,834 → 6,899. `human_confirmed` 774 → **836** · `missing_address` 4,922 → 4,924 · `no_candidates` 1,138 → 1,139 |
| closure | 종료 0, 160초. 대상 업소 32 → **33**, 모두 `unknown`(폐업 대조 전) |
| build | 종료 0, 283초. **마커 33** · 장부 레코드 9,720 |

geocode는 #74의 37분보다 짧았다. 까닭은 따로 재지 않았다.

장부(`records.json`)에서 바뀐 레코드는 65건이다. `목사골농장` 62건은 `pending` → `mapped`, 나머지 3건은
`pending` → `geocode_failed`다. 판단 보류로 남긴 14건은 `pending` 그대로다. 0건으로 숨긴 것은 없다.

LLM 예산 장부(`data/_shared/llm-budget.jsonl`)와 판별 캐시(`data/_shared/classify.jsonl`)는 바이트 그대로다.

## 기관별 산출물은 다시 만들지 않았다

이슈는 해당 기관 산출물도 다시 만들라고 했다. 다섯 벌을 `classify`부터 돌려 보니 **동구·광산구·남구·서구의
산출물이 이미 낡아 있었다.** 네 기관 모두 `classify.json`부터 `build.json`까지의 의존성 해시가 커밋된
`records.csv`(광산구)나 `records.csv`·`parse.json`(나머지 셋)과 맞지 않는다. [#113](issue-113.md)이 다섯 구를
다시 parse하고 "`classify` 뒤 단계는 다시 돌리지 않았다"고 적은 상태 그대로다. 북구만 맞는다.

다시 만들면 #113의 재추출이 함께 들어온다. 레코드가 동구 992 → 995, 남구 1,022 → 1,074, 서구 1,158 → 1,188로
늘고, 서구에는 캐시에 없는 식당 상호가 하나 생겨 새 조회가 필요하다. 이 실행에서는 허용 목록 밖의 질의라
transport가 끊었다(나간 요청 없음). #113 결과를 기관 산출물에 반영하는 일은 이 이슈의 범위가 아니므로
기관 산출물은 **커밋된 그대로 되돌렸다.** 조회 캐시 두 줄만 남는다([새 조회](#새-조회)).

그래서 이번 보정은 도시 산출물에만 반영된다. 동구·서구의 보정 줄은 도시 산출물 안의 두 구 레코드에 걸린다.
사이트는 도시 산출물로 build하므로 지도는 영향을 받지 않는다. `check-data`도 통과한다(아래 [검사](#검사)).

## 기존 확정은 그대로다

커밋된 `geocode.json`(HEAD)과 새 산출물을 레코드마다 맞대 보았다.

- 전에 있던 결과 **6,834건이 모두** 모든 필드까지 같다. 성공 774건의 `business_id`·좌표·확정 상호·사유도
  같다. 바뀐 것은 0건이다.
- 업소는 32곳 → 33곳이다. 새로 생긴 하나가 위 마커이고, 사라진 업소는 없다.
- `markers.json`의 기존 마커 32개는 필드까지 같다. HEAD의 데이터로 따로 build한 결과와 비교했다.
- 판정 이력은 새로 판정한 65건만 쌓였다(`geocode-history-v2.006.jsonl` +65줄). 판정이 바뀌지 않은
  레코드는 `lookup_key`가 그대로라 재사용됐다([ADR-0003](../adr/0003-narrow-geocode-history-key.md)).

## 남은 제한

- **레코드 단위 연결은 없다.** 원본에 주소 열이 없다. 62건을 한 곳으로 본 근거는 기관이 이 상호에 다른 곳을
  한 번도 적지 않았고, 두 제공자가 같은 주소를 준다는 것까지다.
- **같은 이름의 농장이 나주에 있다.** 62건의 목적은 모두 간담회·직원 격려라 식사로 읽었다. 농장에서
  물건을 산 행이 섞였을 가능성은 목적 칸으로만 배제했다.
- **10회 이하의 변형 표기는 확정하지 않았다.** `목사골농장 (서구 치평동)`은 조회 후보가 같은 곳이지만 방문
  1회다. #74와 같이 방문 문턱대로 두었다. 동구 `목사골농장` 1건도 같다.
- **`주식회사 목사골` 7건과 `목사골농장 외 1` 2건은 판단 보류다.** 법인이 어느 업소를 운영하는지, `외 1`이
  무엇인지 가릴 자료가 생기면 다시 판단할 수 있다.
- **기관별 산출물 네 벌은 #113 이후 낡은 채다.** 이번 보정도 기관 산출물에는 반영되지 않았다.
  다시 만들려면 서구 새 조회 1건이 필요하다. #113의 재추출은 도시 산출물에도 들어 있지 않다
  (도시 `parse`를 다시 돌리지 않았다). 따로 다룰 일이다.
- **확정은 에이전트 검토이고 사람의 최종 확인은 이 PR 검토다.** 현장 확인이나 기관 문의는 하지 않았다.
- **`fetch.json`의 원본 경로가 다른 작업 공간의 절대 경로다.** #74와 같이 그 경로를 `--raw-root`로 줬다.
- 화면 확인은 하지 않았다. 브라우저 확인은 [#50](https://github.com/snowjaewon/OfficialDeliciousMap/issues/50)의 절차다.
