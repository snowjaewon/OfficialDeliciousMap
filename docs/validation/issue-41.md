# 이슈 #41 구현 검증

2026-09-11, Windows PowerShell, Python 3.12.10.
범위: [공통 예산을 지키는 지정 건 LLM 후보 비교 #41](https://github.com/snowjaewon/OfficialDeliciousMap/issues/41).

- 공통 USD 15 한도와 예약·정산·누적 보존: [폴백 정책](../specs/header-mapping-fallback.md).
- 지정 모델 `gemini-3.6-flash`와 `thinkingLevel=minimal`: [계정·키 준비 #6](https://github.com/snowjaewon/OfficialDeliciousMap/issues/6#issuecomment-5602124904).
  같은 댓글의 단가(입력 $1.50 / 출력 $7.50 per 1M)는 **외부 집계값이고 재확인 대상**이므로

## 경계

| 모듈 | 소유하는 것 | 소유하지 않는 것 |
| --- | --- | --- |
| `budget` | 한도·예약·정산·누적 보존·집행 잠금 | 모델 호출, 프롬프트, 업소 판정 |
| `gemini` | 요청 구성·응답 해석·사용량 해석·적용 단가 | 잔액 계산, 지정 여부, 사람 확정 |
| `comparison` | 지정·미해결 판단, 추린 입력, 근거 확인, 제안 보존 | 잔액 계산, 복원명·좌표 확정 |
| `storage` | 지정 입력·제안 이력·예산 장부의 직렬화 | 집행 순서, 판정 |

모델 제공자를 바꾸면 `gemini`와 `.env` 단가만 고친다. 공통 한도·판정·사람 확인 규칙은 그대로다.
쓰지 않는 모델용 어댑터나 범용 모델 플랫폼은 만들지 않았다.

## 구현과 TDD

기존 공개 CLI(`geocode`)를 그대로 주 테스트 경계로 쓴다. 새 테스트는 실제 예산 집행·지정 판단·
근거 확인·제안 저장·판정 연결을 실행하고 HTTP 경계에만 합성 응답을 주입한다
(`cli.main(argv, model_transport=..., naver_transport=...)`). 네트워크 차단·임시 디렉터리·합성
선행 산출물을 쓰며 실제 키와 유료 호출은 없다. 비교나 예산 자체를 항상 성공하는 가짜로 바꾸지 않았다.

실패→최소 구현→통과를 확인한 동작(`tests/test_restoration_comparison_cli.py`, 25건):

- 지정한 미해결 건의 제안 보존과 사람 확정 뒤의 판정 변경: 최초 `compare` 검토 입력 부재로 실패.
- 상호 문제가 아닌 미확정(주소 근거 부재)의 무호출: 최초 판정 사유 구분 부재로 실패.
- 추린 후보·근거만 전송, 도구·검색 연동 미구성, 키의 헤더 전달: 최초 `model_transport` 인자 부재로 실패.
- 미지정 건과 이미 해결된 건의 무호출: 최초 지정 판단 부재로 실패.
- 좌표만 없는 건의 무호출(좌표 선택에 모델을 쓰지 않음): 최초 미해결 판정 부재로 실패.
- 근거 없는 제안·후보 밖 상호·사유 없는 답변·잘린 응답·해석 불가·통신 실패·근거 부족의 사유 보존: 최초 근거 확인 부재로 실패.
- 호출 전 예약과 실제 사용량 정산(사고 토큰은 출력 단가, 합계 필드 미중복): 최초 예산 모듈 부재로 실패.
- 사용량 미확인 호출의 예약 유지: 최초 정산 분기 부재로 실패.
- 한도 경계의 무호출과 사람 검토 지속: 최초 한도 검사 부재로 실패.
- 기존 사용액 기록이 없을 때의 무호출: 최초 잔액 가정으로 실패.
- 집행 잠금이 잡혀 있을 때의 무호출·이중 예약 방지와 잠금 해제 후 재시도: 최초 잠금 부재로 실패.
- 실행을 가로지르는 누적 보존: 최초 실행마다 새 장부를 써 실패.
- 변경 없는 실행의 제안 재사용과 후보·근거 변경 시 재요청: 최초 요청 키 부재로 실패.
- 보류된 제안의 `--retry-failed` 한정 재시도와 재시도별 예약 항목 분리: 최초 같은 예약 ID로 실패.
- 단가 미확인 구성의 종료 코드 2와 변수 이름만 노출: 최초 구성 검사 부재로 실패.
- 모델 키가 없을 때 기존 경로 유지: 최초 구성 분리 부재로 실패.
- 인증키·응답 원문·사용량 원문의 산출물 미노출: 최초 비교 미구현으로 실패.
- 조회→지정 비교→사람 확인→좌표 판정→마커까지의 기존 CLI 연결: 최초 비교 경로 부재로 실패.

제안 이력(`restore-proposal-v1.jsonl`)은 geocode 의존성에 넣지 않았다. 제안이 갱신돼도 사람 확인과
기존 판정의 유효성은 그대로이고, 제안만으로 판정이 바뀌지도 않는다. 산출물 envelope 버전은 v4 그대로다.

## 제한

**실제 모델을 한 번도 호출하지 않았다.** 유료 호출을 하지 않았으므로 다음은 남은 확인이다.

- 적용 단가. `.env`에 담당자가 넣는 값이며 제공자 요금 페이지로 확인해야 한다. 확인 전에는 호출되지 않는다.
- 응답 모양. `candidates[0].content.parts[].text`와 `usageMetadata`의
  `promptTokenCount`·`candidatesTokenCount`·`thoughtsTokenCount`를 과금 항목으로 읽는다.
  실제 `gemini-3.6-flash` 응답이 이 이름과 구조를 그대로 주는지는 확인하지 않았다.
  캐시 토큰(`cachedContentTokenCount`)은 현재 별도 단가로 세지 않으므로 명시적 캐시를 쓰면 다시 정해야 한다.
- `thinkingLevel=minimal`과 `responseSchema`의 동시 동작은 #6의 확인을 따랐고 이 구현에서 재현하지 않았다.
- 입력 토큰 상한을 요청 본문 전체의 문자 수로 잡는다. 한국어 1.0~1.2 글자/토큰 실측(#4)에 기댄 근사이며
  실제 토큰이 이보다 많으면 한 요청의 실제 비용이 예약을 넘을 수 있다. 정산은 실제 사용량으로 하므로
  장부에는 실제 금액이 남고 다음 요청부터 반영된다. 출력은 요청의 `maxOutputTokens`로 실제로 묶인다.
- 두 개발자의 공유 집행. 잠금은 동시 실행을 직렬화하는 대신 거절하며(`concurrent_execution`)
  담당자가 다시 실행해야 한다. 잠금 파일은 같은 파일 시스템의 동시 실행만 막는다. 서로 다른 PC의 동시
  실행은 장부 파일을 커밋·동기화해 맞추며, 동기화 전에 각자 호출하면 이중 집행이 가능하다.
  비정상 종료로 잠금이 남으면 담당자가 지워야 한다.
- `prior_usage` 줄의 정확성은 사람이 제공자 사용량·청구 기록으로 확인해 적는 값에 달려 있다.
  이 구현은 값이 없을 때 호출하지 않을 뿐 값 자체를 검증하지 못한다.
- 제안 품질. 합성 응답으로 근거 확인 규칙만 검증했다. 실제 모델이 후보를 얼마나 맞게 고르는지,
  근거 없는 제안이 얼마나 걸러지는지는 실자료로 확인하지 않았다.

헤더 매핑·비식당 판별·전량 추출 폴백은 아직 이 예산 모듈을 쓰지 않는다. 해당 구현이 붙을 때
같은 `budget` 모듈을 거쳐야 하며, 그 전까지 장부의 누적액은 후보 비교와 사람이 적은 기존 사용액만 담는다.
실제 수집기·전체 웹사이트·별도 검토 화면·사용자 대면 AI·배포는 이 범위가 아니다.
합성 테스트 통과는 실제 상호 복원 품질이나 제출 전 미해결 0건의 검증이 아니다.
