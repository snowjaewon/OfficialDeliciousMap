# 합쳐 적은 상호를 사람 확인으로 가른다 (#117)

2026-09-14 실행. 한 칸에 업소 둘 이상이 적힌 상호를 사람 확인으로 업소마다 가르고, 확인이 없는
레코드를 전용 사유로 보류하는 코드 경로를 넣고, **광주 산출물을 그 코드로 다시 만든 기록이다.**
**549건의 전수 판정 자체는 사람 작업이라 이 이슈의 범위가 아니다**(트리아지 브리프의 Out of
scope). 상호 가르기 파일이 아직 비어 있어 이 실행으로 갈린 레코드는 없고 좌표도 늘지 않았다 —
확인을 적어야 는다.

수치는 모두 커밋된 산출물(`data/gwangju/records.csv`·`geocode.json`·`classify.json`)에서 다시
셀 수 있다. 세는 방법은 5절에 있다.

## 1. 합쳐 적은 상호로 읽히는 것 — 636건, 고유 표기 561개

| 구분자 | 예 | 레코드 | 고유 표기 |
| --- | --- | --- | --- |
| 쉼표 | `시골밥집, 데이지` | 443 | 386 |
| 슬래시 | `민소한우/폴바셋` | 80 | 76 |
| `&` | `천손&컴포즈커피` | 19 | 14 |
| `및` | `황금코다리 및 라떼라라` | 7 | 7 |
| 좌표 판정 대상 합계 | | **549** | **483** |
| 판정 대상 아님(판단 보류 80 · 비식당 7) | | 87 | 78 |
| 전체 | | **636** | **561** |

좌표 판정 대상 **549건**은 트리아지 브리프가 센 549건과 같은 수다. 갈래별 수는 브리프의
`쉼표 443 · 슬래시 81 · & 19 · 및 6`과 슬래시·`및`에서 한 건씩 다른데, 이 규칙이 아래 둘을
**한 업소로 남기고** `및`을 공백으로 둘러싸인 낱말로만 읽기 때문이다.

- `지글보글(무등로218번길 60, 신안동)` — 쉼표 앞뒤가 숫자·주소라 천단위·주소 쉼표로 보고 가르지 않는다.
- `옥과한우촌(상무점)/` — 끝에 붙은 슬래시라 나뉜 한쪽이 빈 값이 되므로 가르지 않는다.

`외 N`(`카페말바우 외 1`) 113건은 둘째 업소에 이름이 없어 이 규칙이 **하나도 나누지 않는다.**
별도 이슈의 범위이며 여기서 건드리지 않았다.

## 2. 549건의 사유 분포 — 전과 후

재실행 전 549건의 사유는 `no_candidates` 525 · `missing_address` 22였고 확정은 0건이었다.
사유가 내용(후보가 없다·주소 근거가 없다)이 아니라 **나뉘지 않은 질의어로 조회한 결과**였다.
재실행 뒤 그 549건은 한 갈래로 모인다.

| 사유 | 재실행 전 | 재실행 후 | 좌표 |
| --- | --- | --- | --- |
| `merged_merchant` | — | **549** | 0 |
| `no_candidates` | 525 | 0 | 0 |
| `missing_address` | 22 | 0 | 0 |
| `matched`·`human_confirmed` | **0** | **0** | 0 |
| 합계 | **547**\* | **549** | **0** |

\* 재실행 전의 분모는 그때의 판별 결과로 센 547건이다. 재실행이 같은 규칙으로 다시 판별해
549건이 됐다. 갈래 자체는 같다.

**좌표 확보 수는 0건 그대로이며 0건으로 감추지 않는다.** 상호 가르기 파일이 비어 있어 이
549건은 아직 한 건도 갈리지 않았고, 사유만 내용에 맞게 바뀌었다.

도시 전체의 사유 분포는 이렇다. **확정 774건(`human_confirmed`)이 하나도 바뀌지 않았다** —
완료 기준의 "기존 확정 상호의 판정이 바뀌지 않는다"를 산출물에서 확인한 값이다.

| 사유 | 레코드 |
| --- | --- |
| `missing_address` | 5,092 |
| `human_confirmed` | **774** (재실행 전과 같음) |
| `no_candidates` | 507 |
| `merged_merchant` | 549 |
| 합계(좌표 판정 대상) | 6,922 |

## 3. 무엇이 무엇을 가르는가

| 하는 일 | 누가 | 결과 |
| --- | --- | --- |
| 구분자로 이름 나누기 | 규칙(`merchants.parts`) | **조회만.** 나눈 이름으로 후보를 미리 조회해 `geocode-lookup-v1.jsonl`에 쌓는다 |
| 업소 몇 곳인지 판정 | 사람(`data/manual/<city>/merchants.jsonl`) | 레코드를 가르거나, 한 업소로 확인 |
| 확인이 없는 레코드 | — | `merged_merchant`로 보류. 한 레코드로 그대로 둔다 |

규칙이 업소를 확정하지 않는 이유는 반례가 규칙으로는 구별되지 않기 때문이다. 조회 결과에
들어 있는 `그저,쉼`·`가인 사주,타로`는 쉼표가 이름 안에 든 한 업소다. 같은 모양의
`강진식당, 모먼트오월`은 두 업소다. 둘을 가르는 것은 글자가 아니라 사람이 본 근거다.

천단위 쉼표는 조회 질의어를 가르지 않는다. 광주에 상호 칸에 업소별 금액이 함께 적힌 표기가
8개 있고, 여덟 모두 **슬래시로만** 갈린다.

```text
낙지촌 96,000원 / 엠지(MG)블루 17,500  →  ('낙지촌 96,000원', '엠지(MG)블루 17,500')
살림채식뷔페:101,400원 / 커피쌤 28,000원  →  ('살림채식뷔페:101,400원', '커피쌤 28,000원')
```

`tests/test_merged_merchants_cli.py`가 이 동작을 조회 질의어로 고정한다(TDD).

## 4. 금액과 계약

나뉜 레코드의 금액은 **빈 값**이고 금액은 지출에 남는다([ADR-0007](
../adr/0007-do-not-split-unallocated-amounts.md)). 반씩 나누거나 한쪽에 몰지 않으므로 나누기
전후의 지출 총액은 같다. 광주 현재 산출물의 지출 총액은 `1,340,258,343`원이며, 확인을 적어
레코드가 갈려도 이 수는 그대로다 — 테스트가 가르기 전후의 총액이 같음을 고정한다.

- `Record`: `amount_krw`가 빈 값일 수 있고, 사람이 업소별로 확인한 지출은 `expense`
  (`expense_id`·`amount_krw`)를 갖는다. 장부 CSV에 `expense_id`·`expense_amount_krw` 두 칸이 늘었다.
  `expense`가 붙어 있다는 것이 "사람이 이미 본 지출"이라는 뜻이며, 업소 하나라는 확인도 이 값을 남긴다.
- `GeocodeReason`: `merged_merchant`가 늘었다. 미확정의 다른 사유보다 앞서며, 확정 두 사유
  (`matched`·`human_confirmed`)는 덮지 않는다.
- 판정 키는 `expense`를 **값으로 담지 않는다.** 판정이 거기서 읽는 것은 "사람이 업소별로 보지
  않은 합쳐 적은 상호인가" 하나뿐이라, 키에는 그 사실만 `held_as_merged`로 담는다
  (`identity.held_as_merged`). `Expense`를 통째로 담으면 판정이 읽지 않는 금액이 키를 바꾸는데,
  [ADR-0005](../adr/0005-key-only-what-the-decision-reads.md)가 이름을 대어 뺀 `amount_krw`가
  그 안에 있다. `KEYED_RECORD_FIELDS`는 `record_id`·`merchant` 그대로이고, 구분자가 없는 상호는
  확인이 붙어도 키가 그대로다 — `tests/test_identity.py`가 둘 다 고정한다.
  `identity.POLICY_VERSION`이 `identity-2`에서 `identity-3`이 되므로 이 자료를 다시 돌리면
  판정 이력이 새 키로 쌓인다. 이전 이력은 지우지 않는다.
- `merged_merchant`는 **조회 실패(`lookup_error`)를 덮지 않는다.** 제공자 장애를 보류로 바꾸면
  실행이 `cause=lookup-failed` 없이 종료 0으로 지나간다. 행동 테스트가 이것을 고정한다.
- 산출물 버전: `parse`가 4에서 **5**, `build`가 7에서 **8**, `markers.json`·`records.json`이
  8에서 **9**가 됐다. 이전 판은 `regeneration-required`로 거부하고 `history/`에 보존한다.
- 의존성: `merchants.jsonl`의 파일 해시와 `merchants.POLICY_VERSION`이 parse·geocode에 들어간다.
  확인을 더하거나 고치면 레코드 자체가 달라지므로 **parse부터** 다시 실행한다.

화면은 마커 상세에 금액 미상 방문 수를(모두 금액 미상이면 `합계 미상`), 자료 범위에 업소별로
가르지 못한 지출 수를 낸다. 장부의 금액 빈 값은 `금액 미상`으로 보인다. 자료 범위의 그 줄은
지도에 오르지 못한 수를 말하지 않는다 — 이 수(636건)에는 비식당·판단 보류도, 구분자가 있어도
확정된 레코드도 들어 있기 때문이다. 좌표를 확정하지 못한 수는 `합쳐 적은 상호` 사유로 위 줄이
따로 낸다.

## 5. 세는 방법

저장소 루트에서 PowerShell·Git Bash 공통으로 아래 검사가 통과한다.

```text
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run python -m deliciousmap.ci check-data --data-root data
```

1절·2절의 수는 커밋된 산출물을 `deliciousmap.merchants`의 규칙으로 다시 센 값이다.
`records.csv`의 상호에 `merchants.is_merged`를 적용하고, 그 레코드의 `record_id`로
`geocode.json`의 `results`와 `classify.json`의 `decisions`를 찾아 사유·판정 상태를 센다.

## 6. 광주를 다시 만들었다

계약이 바뀌어 커밋돼 있던 산출물은 이 코드로 읽히지 않았다. `parse`가 v4라 스키마가 맞지 않고,
`identity.POLICY_VERSION`이 바뀌어 `geocode.json`의 판정 키도 맞지 않아
`build city=gwangju org=* cause=regeneration-required`였다. 그래서 `parse`부터 다시 만들었다.

`fetch`·`headermap`은 다시 돌리지 않았다. 두 산출물의 스키마와 의존성이 그대로이고 상류가
하나도 바뀌지 않아, 다시 돌려도 같은 입력을 얻으면서 게시판 원본 요청만 되풀이한다.

```text
uv run --env-file .env python -m deliciousmap parse   --city gwangju
uv run --env-file .env python -m deliciousmap classify --city gwangju
uv run --env-file .env python -m deliciousmap geocode  --city gwangju
uv run --env-file .env python -m deliciousmap closure  --city gwangju
uv run --env-file .env python -m deliciousmap build    --city gwangju
```

| 단계 | 결과 |
| --- | --- |
| `parse` | `parse` v5, 레코드 9,720건(전과 같음). 상호 가르기 파일이 비어 있어 갈린 지출은 0건 |
| `classify` | 모델 호출 3회 USD 0.027. 프로젝트 누적 정산액 USD 0.710 (한도 15) |
| `geocode` | 6,922건 판정. 사유 분포는 2절 |
| `closure`·`build` | `markers.json`·`records.json` v9, 마커 32개·레코드 9,720건 |

**조회.** 나눈 이름 조회가 늘어 조회 캐시가 4,195줄 → 7,206줄(20MB 상한에 닿아 `.002`로 분할)이
됐다. 처음 실행에서 `lookup_error` 71건이 났고 `--retry-failed`를 두 번 돌려 0건이 됐다. 모두
인허가 API의 `unavailable`이었다. 실패를 보류로 덮지 않으므로 그때마다 종료 1이 났다 —
이 사유가 `merged_merchant`에 먹히지 않는 것을 산출물에서 확인한 셈이다.

**이력.** 재시도 두 번이 실패 레코드를 통째로 다시 쌓아 판정 이력이 세 세대(19,218줄·193MB)가
됐다. 커밋하기 전에 아직 커밋된 적 없는 조각을 지우고 `geocode`를 한 번 더 돌려 **한 세대
(59MB)로 줄였다.** 조회 캐시가 다 채워져 있어 제공자 호출은 0회였고, 판정 결과는 레코드마다
`(record_id, reason, lookup_key)`를 모아 낸 지문 `8056b05ebaec14d5`가 줄이기 전후로 같다.
커밋된 적 있는 이력(조각 1~6)은 손대지 않았다.

**화면.** 자료 범위가 `상호 칸에 업소 둘 이상이 적힌 지출 636건`과 좌표 미확정 사유
`합쳐 적은 상호 549건`을 따로 낸다. 마커 상세의 금액 미상 방문 수는 0이다 — 아직 갈린 레코드가
없어 금액이 빈 레코드도 없다. 지출 총액은 `1,340,258,343`원으로 재실행 전과 같다.

그래서 다음 두 가지가 아직 하지 않은 일로 남는다.

- **549건의 전수 판정** — 사람 작업이며 별도 이슈(`ready-for-human`)다. `merchants.jsonl`에
  한 줄씩 쌓아야 레코드가 갈리고 좌표가 는다.
- **남구 `.hwpx` 재실행** — 이 코드가 들어간 뒤에 한다([#112 검증](issue-112.md) 9절).
  재실행 뒤 합쳐 적은 상호는 3건 늘어난다.

## 7. 이 이슈가 하지 않은 것

- **상호 칸의 업소별 금액 배분** — ADR-0007이 예외로 둔 8건(3절)이다. `merchants.jsonl`은
  이름 목록만 받으므로 이 8건도 확인을 적으면 금액이 빈 값이 된다. 없는 숫자를 지어내지는
  않지만 원본이 적은 금액을 아직 쓰지 못한다. 배분을 쓰려면 확인 한 줄이 업소별 금액을 받는
  계약이 더 필요하다.
- **`외 N` 113건** — 둘째 업소에 이름이 없어 나눌 수 없다(1절).
- **지점 특정·줄임말·후보 없음** — [#74](https://github.com/snowjaewon/OfficialDeliciousMap/issues/74)의 범위다.
