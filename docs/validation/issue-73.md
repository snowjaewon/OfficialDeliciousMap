# 이슈 #73 실행 검증

2026-09-13, Windows 11 · Git Bash · Python 3.12.10. 도시는 광주, 기관은 광주광역시청 하나다.
범위는 [인허가 조회를 실제 키로 붙인다 #73](https://github.com/snowjaewon/OfficialDeliciousMap/issues/73)이다.
계약은 [지오코딩](../geocoding.md)에 있다. 실제 `DATA_GO_KR_KEY`로 조회한 첫 실행이다.

## 결론부터

**인허가 조회는 붙었고, 확정 건수는 늘지 않았다.** `matched` 자동 채택은 0건이다.
이유는 인허가 자료의 품질이 아니라 독립 근거(`facts`)가 0건이라는 것이다. 아래에 근거를 적는다.

## 이슈가 잡은 뿌리가 실제와 달랐다

이슈는 뿌리를 "후보 제공자가 네이버 하나뿐"으로 잡았다. 제공자가 하나였던 것은 맞지만,
제공자를 하나 더 붙여도 `matched`는 서지 않는다. `identity.decide_identity`가 후보를 비교하기
**전에** `lookup.facts`를 요구하기 때문이다(`identity.py:120`).

`facts`는 담당자가 준비한 `geocode-input.json`에서만 온다. 제공자 조회는 `candidates`만 채우고
`facts`는 받은 그대로 넘긴다(`lookup.py:103`). 계약이 "후보 출처만을 사실 출처로 반복하면
자동 채택하지 않는다"로 정한 설계이며, 실제로 그렇게 적으면 `insufficient_evidence`로 막힌다.

광주에는 `geocode-input.json`이 없고(`dependencies.candidates`가 `sha256("")`), 레코드 2,232건이
전부 `facts` 0건이다. 실행 전에 인허가가 네이버와 똑같은 상호·지점·주소·좌표를 준 가장 유리한
경우를 만들어 `decide_identity`에 넣어 확인했고, 실행 결과가 그 예측과 같았다.

| 레코드 | facts | 실행 전 예측 | 실행 결과 |
| --- | --- | --- | --- |
| 용전식육식당 | 0 | `missing_address` 그대로 | `missing_address` |
| 나룻배상무점 | 0 | `no_candidates` → `missing_address` | `missing_address` |
| 카멜오르조 | 0 | `human_confirmed` 유지 | `human_confirmed` |

근거는 [이슈 코멘트](https://github.com/snowjaewon/OfficialDeliciousMap/issues/73#issuecomment-5651053118)에
남겼다. `missing_address` 1,679건의 뿌리는 제공자 수가 아니라 **독립 근거 파일이 없다**는 것이다.

## 실제 키로 처음 확인한 것

[#40 검증](issue-40.md)이 "실제 키로 한 건도 조회하지 않았다"로 남긴 항목들이다.
소량 탐침(업종 3종 × 질의 5개)으로 먼저 확인하고 전량 실행했다.

- **`resultCode`의 성공 값은 `"0"`이고 `resultMsg`는 `"정상"`이다.** HTTP 상태 코드가 아니다.
  어댑터는 `"200"`만 성공으로 봤으므로 **실제 키로는 모든 조회가 `unavailable`이 됐다.**
  그대로 돌렸으면 2,232건이 전부 `lookup_error`가 되고 이미 확정된 299건까지 무너진 뒤
  종료 1로 끝났을 것이다. 업종 세 가지 모두 `"0"`을 준다.
- **공백이 든 질의어는 그대로 동작한다.** `명가원 한정식`이 일반음식점 3건을 준다. 목업이 관찰한
  "값에 공백이 들어가면 0건"은 인코딩 문제였고 `%20`으로 이미 없앤 상태였다.
  서로 다른 질의어 1,071개 가운데 248개(23%)에 공백이 있다.
- **응답 모양**: 0건과 한 건 모두 `items` 객체 안의 `item` **목록**으로 왔다. 목록 없는 객체 하나는
  이번 실행에서 관찰하지 않았다. 어댑터는 그 모양도 읽으므로 그대로 둔다.
- **필드 이름**: `BPLC_NM`·`ROAD_NM_ADDR`·`LOTNO_ADDR`·`CRD_INFO_X/Y`·`MNG_NO` 모두 있었다.
- **EPSG:5174 변환**: 조사 #5의 서울 용산 표본 `X 198810.77, Y 448800.97`이
  `37.541464, 126.987332`로 나와 #40의 기대값과 소수점 6자리까지 같다. 광주 세 지점의
  WGS84 → 5174 → WGS84 왕복 오차는 1e-7° 수준이다. 실제 응답 좌표(예: `X 190475.304206016,
  Y 193234.584505321`)도 한반도 범위 안에 들었다. 인허가 후보 48,123건 가운데 **45,669건이 좌표를
  받았고 2,454건은 보류**됐다.

## 실행과 결과

```text
Git Bash: uv run --env-file .env python -m deliciousmap geocode --city gwangju
          uv run --env-file .env python -m deliciousmap geocode --city gwangju --retry-failed
```

서로 다른 질의어 1,071개 × 업종 3종 = **3,213회** 요청, 약 68분. 조회 캐시에 `provider: license`
항목 1,073줄이 쌓였다(`ok` 1,071 · `unavailable` 2). 일시 실패 2건(`다복식당 상무점`,
`칠성골 외 1`)은 `--retry-failed`로 다시 요청해 성공했고, 캐시에는 실패 revision이 그대로 남는다.

| 사유 | 인허가 전 | 인허가 후 |
| --- | --- | --- |
| `human_confirmed` | 299 | **299** |
| `missing_address` | 1,679 | 1,710 |
| `no_candidates` | 254 | 223 |
| `matched` | 0 | **0** |
| `conflicting_evidence` | 0 | **0** |
| 합계 | 2,232 | 2,232 |

- **`matched` 0건**. 위에 적은 대로 `facts`가 0건이라 후보 비교에 이르지 못한다.
- **`conflicting_evidence` 0건**. 좌표 충돌은 두 제공자가 *같은 업소로 확정된 뒤* 좌표가 어긋날 때
  생긴다. 확정에 이른 건이 사람 확인 299건뿐이고 그 경로는 확인한 후보 하나만 보므로
  판정에는 충돌이 남지 않았다. **그러나 겨룰 자리에 가지 못했을 뿐 근거는 실제로 어긋난다.**
  아래를 보라.

### 네이버와 인허가가 같은 업소를 가리킨 건수

완료 기준이 요구한 수치이고, [#40 검증](issue-40.md)이 "실행 초기에 이 비율을 재고"로 남긴
측정이다. 정규화한 상호·지점·주소가 두 제공자에서 똑같은 자리를 셌다.

| 항목 | 건수 |
| --- | --- |
| 근거가 겹친 레코드 | **56** |
| 겹친 서로 다른 업소 표기 | **22** |
| 그중 좌표가 어긋남 | **51** |
| 그중 좌표가 정확히 같음 | **0** |
| 그중 한쪽만 좌표를 줌 | 7 |

**겹친 자리에서 좌표가 정확히 같은 경우는 하나도 없었다.** #40이 예고한
"`pyproj`가 고른 `Korean 1985 to WGS 84 (1)` 변환의 수 m~수십 m 오차 때문에 같은 업소라도
네이버 좌표와 정확히 같지 않다"가 실자료에서 그대로 확인됐다. 지금은 `facts`가 0건이라
이 충돌이 판정까지 오지 않지만, `facts`가 채워지는 순간 이 56건은 `matched`가 아니라
**`conflicting_evidence`로 간다.** 허용 오차를 둘지 말지는 그 전에 정해야 하고, 그 기준은
#33·#36 어디에도 없다. 임의로 정하면 부모 스펙이 금지한 추측 좌표가 된다.

주소 표기가 두 제공자에서 똑같아야 겹치므로 56건은 하한이다. 표기가 달라 못 겹친 자리는
세지 않았다.
- **확정 299건은 그대로다.** 판정이 바뀐 건은 없다.
- `no_candidates`가 31건 줄고 `missing_address`가 31건 늘었다. 네이버에 없던 상호를 인허가가
  주어 "후보 없음"에서 "근거 없음"으로 옮겨간 것이며, 확정이 아니다.
- 인허가 후보를 하나라도 받은 레코드는 1,751건, 하나도 못 받은 레코드는 481건이다.
  한 레코드가 받은 최대 후보 수는 261건이다.

`closure`와 `build`도 이어서 돌려 산출물을 맞췄다. 셋 다 종료 0이다. 마커는 **12개**로 전과 같다
(확정 299 레코드가 업소 12곳으로 묶인다). 레코드는 2,810건이 장부에 남는다. `closure`는 여전히
모두 `unknown`이다.

## 20MB 상한에 걸려 한 번 실패했다

인허가 후보가 붙자 `geocode.json`이 **23.4MB**가 되어 20MB 상한(ADR-0001)을 넘었고, 첫 실행은
`cause=invalid-artifact`로 끝났다. 조회는 이미 캐시에 쌓인 뒤였다.

`cond[BPLC_NM::LIKE]`는 전국 부분일치라 흔한 상호일수록 결과가 많다. 서로 다른 질의어 1,071개
가운데 340개는 0건, 438개는 1~9건인데 **130개 조회가 업종별 100건 상한에 닿았다**. 그 상호는
서비스 쪽에서 이미 잘린 임의 조각이다. 레코드마다 후보를 실으면 48,123건이 된다.

사용자 결정에 따라 **후보를 하나도 버리지 않고 산출물을 조각으로 나눴다.** 계약이 예고한
방향이다("산출물 파일은 각각 20MB 이내로 나누며"). 결과는 아래와 같고 모두 상한 아래다.

| 파일 | 바이트 |
| --- | --- |
| `geocode.json` | 19,999,077 |
| `geocode.002.json` | 3,445,792 |
| `geocode-history-v2.jsonl` | 15,477,093 |
| `geocode-history-v2.002.jsonl` | 16,855,988 |
| `geocode-history-v2.003.jsonl` | 19,997,863 |
| `geocode-history-v2.004.jsonl` | 4,033,242 |
| `geocode-history-v2.005.jsonl` | 19,964,006 |
| `geocode-history-v2.006.jsonl` | 2,182,960 |
| `geocode-lookup-v1.jsonl` | 9,736,052 |

이력이 .003~.006으로 늘어난 것은 2,232건의 `lookup_key`가 모두 바뀌었기 때문이고(조회 결과가
판정 키에 들어간다), .005·.006은 `--retry-failed`가 남긴 재시도 revision이다.

## 구현과 TDD

실패 → 최소 구현 → 통과 순서로 세 가지를 고쳤다.

1. **`resultCode` 성공 값**(`fix(licenses)`). 실측 봉투(`"0"`/`"정상"`)를 성공으로 읽는 테스트가
   `cause=lookup-failed`로 실패했다. `SUCCESS_CODE`를 `"0"`으로 고치고
   `INTERPRETATION_VERSION`을 `food-license-2`로 올렸다. 앞 버전으로 이미 조회한 사람의 캐시에는
   실패만 쌓여 있으므로 키를 갈라 재시도 없이 되읽지 않게 한다. 합성 응답도 실측 봉투에 맞췄다.
2. **산출물 조각 분할**(`feat(storage)`). 레코드 3건에 후보를 잔뜩 실어 상한을 낮춘 테스트가
   실제 운영과 같은 `cause=invalid-artifact`로 실패했다. `PARTITIONED_PAYLOAD`에 나눌 단계와
   목록 칸을 선언하고, `artifact_contents`가 쓸 조각을 모두 만들어 크기를 확인한 뒤에야
   `write_artifact`가 쓴다. 이력이 산출물보다 먼저 쌓이므로 순서를 지켜야 부분 기록이 남지 않는다.
   `read_artifact`가 번호 순으로 이어 읽고 봉투 머리가 다른 조각을 거부하며, `artifact_digest`가
   조각을 모두 해시해 뒤 조각만 바뀐 낡음도 `closure`·`build`가 잡는다.
3. **조각 크기 계산**(`fix(storage)`). `json.dumps`의 기본 구분자는 쉼표와 공백 두 자인데 한 자로
   셌다. 광주 실행에서 첫 조각이 **20,001,605바이트**로 정확히 그 조각의 항목 수만큼 넘쳤다.
   쓰기 전 크기 확인이 잡아 거부했으므로 넘친 파일이 남지는 않았다. 작은 항목 200개를 작은
   상한으로 나누는 테스트로 고정했다.

결과 하나가 혼자 상한을 넘으면 나눌 자리가 없으므로 전과 같이 거부한다. 합쳐서만 넘치던 경우는
이제 거부 대신 나뉜다. 그 두 동작을 각각 테스트로 고정했다.

## 제한

- **확정 건수는 늘지 않았다.** 이 실행이 만든 것은 마커가 아니라 사람 확인의 재료다.
  인허가 후보 48,123건과 그 좌표 45,669건이 산출물과 조회 캐시에 남는다.
- **`matched`를 얻으려면 `facts`가 필요하다.** `geocode-input.json`을 만드는 일은 사람이 근거를
  확인하는 작업이고 이 이슈의 범위가 아니다. [#93](https://github.com/snowjaewon/OfficialDeliciousMap/issues/93)과
  겹치는 부분을 정리해야 한다.
- **조회당 첫 100건만 본다.** 130개 조회가 그 상한에 닿았으므로 그 상호의 실제 업소는 응답에
  없을 수 있다. 그때는 후보가 맞지 않아 미확정으로 남을 뿐 다른 업소를 채택하지는 않는다.
- **남긴 후보의 85%가 다른 시도다.** `cond[BPLC_NM::LIKE]`는 전국 부분일치이므로 후보 48,123건의
  주소는 경기도 10,387(22%)·서울특별시 9,730(20%)·전남광주통합특별시 7,368(15%)·경상남도
  2,564(5%) 순이다. 20MB를 넘긴 것은 대부분 이 다른 시도 후보다. 그래도 거르지 않는 이유는
  계약이 "기관 도시 밖 후보를 거르거나 기관 도시 안 동명이 업소로 바꾸지 않는다"로 정했기
  때문이다. 거르면 광주 안의 동명이 업소를 정답으로 밀어 올리게 된다.
- **확정된 레코드도 조회했다.** 이슈는 "미확정 레코드만 조회한다"고 적었지만, 계약의 조회 대상은
  "후보가 비어 있고 담당자가 조회 실패를 적어 두지도 않은 레코드"다(판정 결과가 아니라 후보
  유무가 기준이다). 후보 파일이 없으므로 확정 299건에도 인허가 질의가 나갔다. 판정은 바뀌지
  않았지만, 이번에 난 일시 실패 2건이 확정 레코드의 것이었다면 그 확정이 `lookup_error`로
  무너졌을 것이다. 계약을 이슈 문구에 맞출지는 별도로 정해야 한다.
- **질의어가 상호로 쓸 수 없는 것이 섞여 있다.** `본도시락 외 1`, `나룻배, 아사커피`,
  `동원식육식당(서구 치평동)` 같은 표기는 사업장명 부분일치로 맞을 수 없다. 상호 복원의 범위다.
- **일일 트래픽 제한을 확인하지 않았다.** 3,213회가 한 번에 지나갔으나 제한값 자체는 보지 않았다.
  도시를 늘리면 먼저 확인해야 한다.
- **영업상태로 후보를 거르지 않았다.** 같은 자리의 폐업·재개업이 몇 건인지도 세지 않았다.
  `closure`는 여전히 `unknown`이다.
