# 이슈 #29 지도 구현·성능 검증 기록

검증일: 2026-09-11(구현), 2026-09-12(광주 실측). 범위: [이슈 #29](https://github.com/snowjaewon/OfficialDeliciousMap/issues/29).
초기 성능 기준은 [이슈 #22 결정 댓글](https://github.com/snowjaewon/OfficialDeliciousMap/issues/22#issuecomment-5614661364)을 따른다.

## 구현 결과

- `build` v5는 선택 도시의 축약 마커를 `markers.json`, 전체 장부를 `records.json`으로 분리한다.
  장부에는 비식당·판단 보류·지오코딩 실패 레코드와 지도 포함 상태를 함께 남긴다.
- build는 7개 도시 랜딩, 도시별 정적 진입 페이지, 공유 CSS·JavaScript, manifest와 service
  worker를 만든다. 도시별 `MapBounds`를 네이버 지도의 초기 `fitBounds`, `minZoom`,
  `maxBounds`에 사용한다.
- 지도 화면은 선택 도시 전체 마커를 대상으로 식당명 검색과 방문 횟수 구간 필터를 적용하고,
  전체 결과와 현재 지도 영역 결과를 따로 표시한다. 마커 상세에서 방문 횟수·폐업 표시와
  네이버 지도 링크를 제공한다. 도시 경계 밖 좌표도 도시 전체 검색 결과에서 선택할 수 있고,
  지도 이동 제한 밖이라는 안내와 상세를 표시한다.
- 장부 파일은 장부 탭을 처음 열 때만 요청하며 100건씩 표시한다. 모바일 너비에서는 마커
  상세가 화면 하단 시트로 배치된다.
- `window.deliciousmapMetrics`에 `marker-data`, `first-ready`, `filter-result`,
  `marker-selection`, `records-first-list`의 최근 200개 시간을 밀리초 단위로 남긴다.
  같은 이름의 `deliciousmap:metric` 이벤트도 발생시켜 측정 자동화가 값을 수집할 수 있다.
  사용자 조작 시간은 이벤트 시각부터 다음 렌더링이 끝날 때까지 재며,
  `window.deliciousmapMetricsSummary(<이름>)`으로 횟수·두 번째로 느린 값·최대값을 확인한다.

### 측정 조건

- 코드 `8dd11ab`(측정 하네스 커밋), 깨끗한 작업 트리. 명령은 README의
  [지도 성능 측정](../../README.md#지도-성능-측정)이며 원본 결과는
  [`issue-29/gwangju-2026-09-12.json`](issue-29/gwangju-2026-09-12.json)에 있다.
- 호스트: Windows 11 Home 10.0.26200, Intel Core i5-1155G7(논리 8코어), 메모리 16GB, AC 전원,
  전원 구성 `균형 조정`. GPU는 Intel Iris Xe(ANGLE Direct3D11)이며 GPU 합성을 쓴다. 측정 전용
  호스트가 아니다. 측정을 멈춘 상태에서도 전체 CPU 사용률이 평균 30%(2초 간격 3회)였고 상주
  프로그램이 여럿 돌았다.
- 브라우저: Chrome 152.0.7977.83 headless(new). Node.js v24.17.0. 헤드리스도 위 GPU를 쓰는 것을
  `SystemInfo.getInfo`로 확인했다. 헤드리스에는 화면 주사율이 없다. 측정 뒤 하네스에 넣은 rAF 간격
  중앙값은 두 환경 모두 16.7ms(60Hz)였고, 이번 결과 JSON에는 이 값이 없다.
- 데스크톱: 1440×900, DPR 1, 네트워크·CPU 제한 없음.
- 모의 모바일: 412×915, DPR 2.625, 터치 에뮬레이션, 다운로드 10Mbps·업로드 1Mbps·지연 100ms·
  CPU 4배 감속. 재방문 요청은 서비스 워커가 받으므로 워커에도 같은 네트워크 조건을 건다.
  워커 제한을 빼면 재방문이 짧아지는 것으로 이 조건이 실제로 걸리는 것을 확인했다.
- 서버: 하네스 내장 서버가 `cache-control: public, max-age=0, must-revalidate`, 약한 ETag,
  gzip으로 보낸다. 운영 Pages는 brotli일 수 있어 전송량은 운영보다 크거나 같다.
- 첫 방문은 매번 새 브라우저 컨텍스트(HTTP 캐시·서비스 워커 없음)에서 연다. 첫 준비 뒤 1초
  기다렸다가 검색·선택·필터·줌·드래그·장부 순으로 조작한다. 재방문은 캐시와 서비스 워커를
  채운 컨텍스트에서 새 탭으로 20회 열었고 20회 모두 서비스 워커가 제어했다.
- 검색어는 방문이 가장 많은 마커 상호의 첫 글자 한 자, 필터는 `1–4`다.
- 식당 선택은 검색 결과 첫 항목을 누른다. 지도 위 마커를 누르는 경로는 재지 않았다. 앱에는 상세와
  별도인 선택 강조가 없으므로 선택 피드백과 상세는 같은 화면 반영을 두 방법으로 잰 값이다.
- 조작은 CDP 마우스·키 이벤트다. 모의 모바일도 터치 에뮬레이션만 켜고 터치 이벤트는 보내지 않는다.
- 피드백은 Event Timing으로 잰다. 8ms 단위로 반올림되며 16ms 미만은 16ms로 적는다. 그렇게 적은
  회차는 데스크톱 검색 입력 2회뿐이다. 결과·상세·장부 첫 목록은 앱의 `window.deliciousmapMetrics` 값이다.

### 성능 기록 판정 (#78, 2026-09-12)

이전 rAF 값은 진단용으로 남기고, 이번에는 각 드래그·줌·장부 스크롤 구간에 CDP
`Tracing`을 붙였다. `console.timeStamp` marker 사이의 `PipelineReporter` 표시 프레임을
기준으로 하며, 60Hz 한 프레임(16.7ms)의 두 배인 33.3ms 이상 간격을 **끊김**, 100ms
이상 간격 또는 100ms 이상 Long Animation Frame·긴 작업을 **멈춤**으로 정의했다. 20회
모두 끊김·멈춤이 없어야 조작 판정을 충족으로 적고, 긴 작업의 URL이 `naver.com`이면
네이버 SDK, 로컬 앱 URL이면 애플리케이션으로 귀속했다. URL이 없는 compositor 작업은
미분류로 남겼다. 원본 120개 trace는 저장소 밖 gzip 파일이며, 커밋된 축약 검증 보고서만
[`issue-78-gwangju-2026-09-12.json`](issue-29/issue-78-gwangju-2026-09-12.json)에 남겼다.

| 모의 모바일 | 장부 스크롤 | 20 | 0 | 20 | 20 | 333.5ms | 0 | 미달 |

모의 모바일 줌의 긴 프레임은 네이버 SDK 27건(총 1,719.7ms)과 애플리케이션 15건
(총 1,044.4ms), 드래그는 네이버 SDK 6건(362.2ms)과 애플리케이션 8건(494ms)이 겹친
구간으로 귀속됐다. 이는 URL이 포함된 스크립트 작업의 원인 단서이지 지도 SDK 전체의
책임을 증명하지 않는다. 한 긴 프레임 안에 두 출처의 긴 작업이 겹치면 자식 작업을 출처별로
나눠 세어 한쪽 출처로 임의 귀속하지 않으며, 합계가 같으면 `dominant`도 `mixed`로 남긴다.
데스크톱의 끊김과 모바일 장부 스크롤의 멈춤은 긴 작업 URL
근거가 없어 미분류로 남겼으며, 다음 개선에서 별도 프로파일링이 필요하다.

### 원인 진단

모의 모바일 미달 항목을 같은 조건의 별도 진단 실행(각 1~3회)으로 나눠 봤다. 이 값은 위 결과
JSON에 넣지 않았다.

- 재방문: 문서 응답 139ms, 셸의 304 재검증 339ms 뒤 네이버 SDK 요청이 755ms에 시작한다. 그 사이
  스크립트 없이 스타일·레이아웃·페인트만 하는 긴 애니메이션 프레임이 480~690ms 있다. 이어서 SDK
  실행 115~242ms, 지도 생성 뒤 스타일 JSON 콜백에서 590~850ms 긴 프레임이 있다. 대부분 네트워크가
  아니라 메인 스레드 CPU다. 다만 서비스 워커가 network-first여서 재방문에도 셸·데이터 요청이 모두
  재검증을 거치고 캐시로 줄어드는 시간이 거의 없다. 이 전략은 우리 코드이며 목표 초과는 약 80ms다.
- 검색 입력 피드백: 입력부터 다음 표시까지 64~136ms 중 검색 `input` 처리 42~85ms, 이후 표시 지연이
  18~44ms다. CPU 프로필에서 처리 중 JS는 네이버 마커 `setMap(null)`의 리스너 정리 위주로 작고 나머지는
  네이티브 렌더링 작업이다.
- 검색 결과 선택 피드백: `click` 처리 58~65ms에 상세 시트 렌더링과 `map.morph` 시작이 함께 들어 있다.
- 전송·파싱은 병목이 아니다. 장부 첫 목록이 목표 안이고 markers.json은 2.8KB다. 마커는 12개라
  마커 그리기도 병목이 아니다. 결정의 개선 수단인 필드 축약·파일 분할과 뷰포트 모드는 위 원인에
  맞지 않아 적용하지 않았다. 재방문에는 원인에 맞는 조치로 셸을 캐시에서 먼저 내주는 서비스 워커
  전략이 남아 있고 아직 시도하지 않았다.

시도했지만 넣지 않은 변경이 셋 있다. (a) 지도 유형을 기본 지도 하나만 등록, (b) 보이는 상태가
바뀐 마커에만 `setMap`, (c) `morph`를 상세 시트가 그려진 뒤로 미룸. build 산출물의 `app.js`만
임시로 고쳐 모의 모바일에서 5회씩 차례로 쟀다. 5회 비교 결과는 저장소에 넣지 않았다.

| 변경 | 첫 방문 | 재방문 | 검색 입력 피드백 | 필터 버튼 피드백 | 선택 피드백 | 선택 상세 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 없음 | 1,816 / 2,643 | 2,227 / 2,379 | 96 / 176 | 64 / 120 | 80 / 128 | 92 / 185 |
| (a) | 2,259 / 3,939 | 1,957 / 2,501 | 96 / 136 | 48 / 112 | 120 / 168 | 125 / 174 |
| (a)+(b)+(c) | 3,017 / 4,090 | 2,048 / 2,249 | 112 / 136 | 64 / 96 | 160 / 288 | 55 / 93 |

값은 중앙값 / 최대(ms)다. 변경과 무관한 첫 방문이 1.8초에서 3.0초로 움직일 만큼 흔들려 어느
변경도 개선이라고 가를 수 없었다. 5회는 결정의 20회보다 적고, 번갈아 재지 않고 차례로 재서
시간에 따른 호스트 변동이 그대로 섞였다. 이 세션에서 같은 조건의 첫 방문은 1.4~4.2초, 재방문은
1.3~4.0초로 흔들렸다. 근거 없는 변경은 넣지 않았다.

### 판정

- 데스크톱: 9개 시나리오 모두 충족했다.
- 모의 모바일: 위 20회에서 첫 방문, 장부 첫 목록, 검색·필터 결과, 선택 상세는 충족했고 재방문과
  입력·선택 피드백 셋은 미달이었다. 같은 세션의 다른 실행에서 첫 방문이 4,000ms를 넘은 적도 있어
  이 호스트의 모의 모바일 판정은 충족·미달 모두 **잠정**이다.
- 실제 Android Chrome·iPhone Safari: 기기가 없어 **미측정**이다.
- 드래그·줌·스크롤: #78에서 CDP 성능 기록으로 판정했다. 데스크톱과 모의 모바일 모두
  적어도 한 조작에서 끊김이 있어 **미달**이며, 모바일 줌·드래그의 긴 작업은 네이버 SDK와
  애플리케이션 단서를 분리했지만 나머지는 미분류다.
- 지도 마커를 직접 누르는 선택, 실제 터치 입력: **미측정**이다.
- 6개 도시: 정제 산출물이 없어 **미측정**이다.

## 측정 절차

같은 코드 커밋에서 도시를 build하고 아래 명령을 실행한다.

```text
양쪽 공통: node scripts/measure_map.js --city <city> --out <결과.json> --trace-dir <저장소 밖 경로>
```
하네스는 결정의 20회 절차, 캐시 초기화, 서비스 워커를 포함한 재방문, 모의 모바일 조건을
자동으로 적용하고 표를 출력한다. 결과 JSON에는 코드 커밋, 작업 트리 상태, 파일 크기·해시,
호스트·브라우저·GPU, 회차별 값과 조작별 CDP 성능 기록 요약이 남는다. 원본 trace는 저장소
밖에 두고 결과 JSON에는 이벤트를 넣지 않는다. 개선 전후는 같은 호스트·같은 명령으로 재고
이 문서와 결정 티켓에 근거를 연결한다. 실제 기기 확인은 여전히 #76 범위다.

기존 광주 시간·rAF 결과는 `8dd11ab`의 하네스로 쟀다. 그 뒤 코드 리뷰를 반영해 CDP 응답
제한 시간, Chrome 기동 실패 정리, 회차 중간 실패의 단계별 기록(`failures`), 필터 초기화
반영 뒤 줌 측정 시작, 피드백 판독 전 두 프레임 대기, rAF 간격 중앙값, 선택 시나리오 이름을
고쳤다. #78의 최종 성능 기록은 `58b040b`에서 2026-09-12에 같은 광주 산출물로 다시 쟀고,
조작 marker 경계와 trace 요약을 결과 JSON에 추가했다.
