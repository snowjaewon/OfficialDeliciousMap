# 이슈 #77 재방문 셸 캐시와 실데이터 성능 재측정

검증일: 2026-09-13. 범위: [이슈 #77](https://github.com/snowjaewon/OfficialDeliciousMap/issues/77).
초기 성능 목표와 20회 판정은 [이슈 #22 결정 댓글](https://github.com/snowjaewon/OfficialDeliciousMap/issues/22#issuecomment-5614661364)을 따른다.

## 서비스 워커 결정과 구현

- 셸 요청(도시 HTML 탐색, `assets/app.js`, `assets/styles.css`, `manifest.webmanifest`)은
  stale-while-revalidate로 처리한다. 캐시가 있으면 즉시 반환하고 네트워크 응답은 뒤에서
  캐시에 덮어쓴다. 캐시가 없으면 네트워크 응답을 기다린다.
- 설치할 때 공통 루트 셸과 함께 **워커를 등록한 도시 화면**을 셸 캐시에 담는다. 첫 방문
  화면은 워커가 제어하기 전에 받았으므로, 이것이 없으면 사용자의 첫 재방문은 도시 HTML을
  여전히 네트워크에서 기다린다. 이 화면을 받지 못해도 설치는 계속하며, 다음 탐색 응답으로
  캐시된다. 7개 도시의 셸을 합성 입력으로 미리 만들지 않는다.
- `markers.json`과 `records.json`은 네트워크 우선이다. 성공한 응답만 캐시에 저장하고,
  네트워크가 실패할 때 마지막 성공 응답을 반환한다. 따라서 검색·집계에 쓰는 마커는
  재방문 때 오래된 캐시를 먼저 확정하지 않는다.
- 다른 출처(네이버 SDK·지도 타일) 요청은 가로채지 않는다. 이전 워커는 모든 GET을
  `fetch`로 대신 받았다.
- 셸 캐시는 `deliciousmap-shell-v1`에서 `deliciousmap-shell-v2`로 올렸고 데이터는
  별도 `deliciousmap-data-v1`에 둔다. 새 워커가 활성화되면 이전 셸 버전만 삭제하고
  `clients.claim()`으로 열린 페이지를 제어한다. 셸 계약을 바꾸는 배포는 셸 이름을
  다시 올려 셸 캐시를 비운다. 같은 버전의 자산 배포는 한 번 오래된 셸이 보일 수 있지만,
  백그라운드 갱신 뒤 다음 탐색부터 새 셸을 사용한다.

- 셸 판별 경로는 워커 스크립트 위치를 기준으로 푼다. 사이트를 하위 경로에 배포해도 공유
  자산이 셸로 처리된다. 측정 뒤 넣은 수정이며 루트 배포에서는 판별 결과가 같다.

**적용 여부: 이 브랜치는 적용한 상태이고, 유지 여부는 triage 결정을 기다린다.**

- 동작은 실제 Chrome에서 확인했다([아래](#실제-chrome의-응답-출처)). 첫 재방문부터 셸이
  캐시에서 나오고 `markers.json`만 네트워크를 거친다.
- 성능 이득은 입증하지 못했다. 20회 번갈아 비교에서 재방문 느린 순 2번째 값은 1,510.7ms에서
  1,940.3ms로 오히려 컸다. ABBA 짝의 평균 차이도 +1.9ms다. 호스트·순서 변동이 셸 재검증
  왕복(지연 100ms) 두세 번보다 크다.
- 개선 후가 빠른 값은 첫 짝(−267.7ms)과 저장소에 남기지 않은 진단(아래)뿐이다. 첫 짝이
  다른 짝보다 조용했다는 증거는 없다. 유휴 CPU는 3·4짝이 더 낮았다.
- 적용하면 셸·데이터 캐시가 분리되고, 오프라인 폴백이 새 마커를 가리지 않는다.
- 대가는 같은 셸 버전으로 배포한 직후 한 번 옛 셸이 보이는 것이다.

## 재방문 비교 해석

블록별 재방문 5회의 중앙값(ms)이다. 짝은 ABBA 순서에서 이웃한 두 블록이다.

| 짝 | 먼저 잰 블록 | 나중 블록 | 개선 후 − 개선 전 |
| --- | --- | --- | ---: |
| 1 | 개선 전 952.4 | 개선 후 684.7 | −267.7 |
| 2 | 개선 후 1,455.0 | 개선 전 1,160.8 | +294.2 |
| 3 | 개선 전 1,427.8 | 개선 후 1,203.9 | −223.9 |
| 4 | 개선 후 1,375.6 | 개선 전 1,170.7 | +204.9 |

- 네 짝 모두 나중에 잰 블록이 빨랐다. 짝 안의 순서 효과가 변형 차이만큼 커서 ABBA로
  상쇄하면 평균 차이가 +1.9ms로 거의 0이다. 같은 변형도 블록 중앙값이 개선 전 952~1,428ms,
  개선 후 685~1,455ms로 흔들렸다.
- 첫 짝(−267.7ms)과 측정 뒤 따로 돌린 진단에서는 개선 후가 빨랐다. 진단은 4회 중앙값이
  개선 전 921ms, 개선 후 641ms였고, 아래 2회는 891·906ms 대 574·595ms였다. 셸 재검증
  왕복 두세 번을 건너뛰는 규모다. 진단은 판정에 쓰지 않았고 저장소에 남기지 않았다.
- 블록의 첫 재방문은 두 변형 모두 자주 느렸다. 개선 후 네 블록에서는 모두 블록 안에서 가장
  느리거나 두 번째였다(862.5·1,642.8·1,350.4·2,344.1ms). 개선 전 네 블록 중 셋도 그랬다
  (1,046.9·1,658.5·1,495.9ms). 2,344.1ms는 40회 중 최댓값이다. 개선 후 첫 재방문 가운데
  셋에서는 페이지 세션에 162~303KB가 잡혔다. 같은 출처 응답은 워커가 내주므로 이는 다른
  출처(네이버 SDK·타일) 응답이다. 준비 단계 직후 이를 받는 하네스 조건의 영향으로 추정한다.
  첫 재방문의 셸 자체는 캐시에서 나왔다([응답 출처](#실제-chrome의-응답-출처)).
- 20회 판정은 호스트 변동에 민감하다. 같은 개선 전 워커가 1차 비교에서는 2,133.4ms로
  미달, 이번에는 1,510.7ms로 충족이었다. 재방문 판정은 목표 근처라 잠정으로 읽는다.
- 결과 JSON의 재방문 `transferred_bytes`는 변형끼리 비교할 수 없다. 이전 워커는 다른 출처
  요청도 대신 받아 그 바이트가 페이지 세션에 잡히지 않는다(항상 467B). 개선 후 워커는 이를
  가로채지 않아 네이버 SDK·타일을 받는 회차에서 수십~수백 KB가 페이지에 잡힌다.

### 1차 비교: 도시 화면 설치 캐시 전

설치 캐시를 넣기 전 워커(`sw.js` `133aebb6…`, 하네스 `6f3ed0b`)로 같은 ABBA 순서를 쟀다.
결과 JSON: [개선 전](issue-77/round1-gwangju-before.json), [개선 후](issue-77/round1-gwangju-after.json).

| 시나리오 | 개선 전 | 개선 후 |
| --- | --- | --- |
| 재방문 | 2,133.4ms 미달 | 2,053.4ms 미달 |
| 검색 입력 피드백 | 104ms 미달 | 88ms 미달 |
| 필터 버튼 피드백 | 80ms 미달 | 64ms 미달 |
| 검색 결과 선택 피드백 | 192ms 미달 | 264ms 미달 |

나머지 5개 시나리오는 두 변형 모두 충족했다. 개선 후 블록 네 개 중 세 개에서 첫 재방문이
가장 느렸다(2,053·2,110·1,767ms). 이를 살피다가 첫 방문 화면이 셸 캐시에 없는 구조를 찾아
설치 캐시를 더했다. 재측정에서도 첫 재방문이 느린 현상은 남았으므로, 이 현상의 원인은
위 해석대로 하네스 조건이다. 설치 캐시는 그와 별개로 셸의 빈틈을 메운다.

2차 측정에서는 한 블록이 Chrome 시작 중 `DevToolsActivePort` 파일 잠금(EBUSY)으로 실패했다.
하네스가 잠긴 포트 파일을 다음 폴링에서 다시 읽도록 고치고 8블록을 모두 다시 쟀다.
위 [결과](#결과-광주-모의-모바일-20회)가 그 재측정이다.

## 실제 Chrome의 응답 출처

최종 워커(`sw.js` `8b434e0c…`)와 개선 전 워커로 각각 2회 진단을 돌렸다. 재방문의 같은 출처
응답 출처(CDP `serviceWorkerResponseSource`)는 다음과 같았다.

| 요청 | 개선 전 | 개선 후 |
| --- | --- | --- |
| `/gwangju/`(첫 재방문 포함) | network | cache-storage |
| `/assets/app.js`, `/assets/styles.css` | network | cache-storage |
| `/gwangju/markers.json` | network | network |

## 하네스 보강

- `measure_map.js`는 Chrome 기동 전 10초 유휴 CPU를 `idle_cpu_percent`, 실제로 내준 셸 파일의
  SHA-256을 `shell`로 남긴다. 개선 전후처럼 같은 커밋의 하네스로 다른 셸을 잴 때 커밋이
  아니라 해시로 변형을 구분한다.
- `--merge`는 번갈아 잰 블록을 합쳐 20회로 다시 판정한다. 셸·데이터·측정 조건·호스트·코드
  커밋이 다른 블록은 합치지 않고, 실패 회차에 블록 번호를 남긴다.

제거를 확인한다.

## 미측정과 후속

- 서울·부산·대구·인천·대전·울산은 정제 산출물이 없어 미측정이다([#75](https://github.com/snowjaewon/OfficialDeliciousMap/issues/75)).
- 광주 마커 12개는 한 1.5km 상자에 모여 있어 마커 밀집 부하가 부족하다.
  [#73](https://github.com/snowjaewon/OfficialDeliciousMap/issues/73) 이후 밀집 구간은 미측정이다.
- 피드백 미달의 원인이 네이버 SDK·초기 렌더링 CPU인지는 이번에 확인하지 않았다. 확인 전에는
  결정의 개선 수단 밖이라고 판단하지 않는다.
- 셸 캐시 무효화는 "셸 계약을 바꾸면 셸 이름을 올린다"는 사람 규칙에 기댄다. 이를 강제하는
  검사는 없다. 규칙을 빠뜨리면 한 번은 옛 셸과 새 데이터가 함께 쓰일 수 있고, `app.js`는
  데이터의 `schema_version`을 확인하지 않는다.
- 유효한 전후 수치에서 목표를 바꿀 근거가 나오지 않아 [#22](https://github.com/snowjaewon/OfficialDeliciousMap/issues/22)의
  기준과 개선 순서를 수정하지 않았다.
