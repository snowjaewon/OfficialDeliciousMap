# 이슈 #69 재게시 사람 확정 검증 기록

2026-09-13, Windows 11 · Git Bash · Python 3.12.10. 도시는 광주, 기관은 광주광역시청 하나다.
기준은 [ADR-0006](../adr/0006-human-confirmed-reposts.md)이며 그 앞의 결정은
[ADR-0004](../adr/0004-merge-repeated-reposts.md)다. 작업 브랜치의 기반은 `develop` `846fce2`다.

## 넣은 것

- 사람 확정 입력 `data/manual/<city>/repeats.jsonl`. 한 줄은 지출 하나
  (`기관·부서·집행일·상호·금액`)와 그 지출을 실은 원본 해시를 범위로 선언하고
  `same_expense`/`separate_expenses` 중 하나를 근거와 함께 적는다(`RepeatConfirmation`).
- `parse`가 이 입력을 읽어 [ADR-0004](../adr/0004-merge-repeated-reposts.md)의 기준보다 먼저
  적용한다. `같은 지출`은 선언한 원본을 잇고, `별개 지출`은 잇지 않으면서 그 지출을 그 원본 쌍의
  재게시 근거에서도 뺀다.
- `parse.json`의 `repeated_expenses`에 `confirmed_*`(확정이 기준보다 더 합친 수)와
  `separate_*`(확정으로 남긴 수)가 생겼다. 기준이 합친 수(`merged_*`)와 섞지 않는다.
- 장부에 없는 묶음이나 그 지출을 싣지 않은 원본을 가리키는 확정은 `parse`가 거부한다.

앞 원본의 기간을 포함하는데 그 안에 2026-02-27 지출은 뒤 원본에도 한 건뿐이고, 사용자·집행목적·
대상인원수·결제방법까지 앞 원본과 같다. 별개 지출이었다면 1~6월을 담은 뒤 원본이 그 날짜에 두 행을
실어야 한다. 앞 원본은 1분기를 다 담고도 한 건만 실었다.

### 119대응과 2026-01-14 · 480,000원

뒤 원본은 대상기간을 2월로 밝히고도 **연번 1에 1월 지출을 그대로 실었다.** 1월은 그 원본의
대상기간 밖이므로 1월부터 누적해 다시 실은 것이다. 같은 부서의 `3월`·`4월`·`5월` 원본도 같은 누적
방식이라 겹치는 지출 2건으로 이미 합쳐져 있었다(#63). 이 확정으로 다섯 원본이 한 지출이 된다.

| 남는 레코드 | `repeats`에 남은 원본 |

남기는 레코드는 ADR-0004 그대로 **가장 먼저 게시된 원본**의 것이다. 119대응과는 확정으로 1월
원본이 묶음에 들어오면서 남는 레코드가 `72b2d46c`에서 `abb05d7b`로 바뀌었고, 다섯 원본이 모두
`repeats`에 남는다. 원본별 보고도 함께 움직인다 — `0930fe8d`는 `records` 3 → 2 · `repeated`
0 → 1, `72b2d46c`는 `records` 2 → 1 · `repeated` 0 → 1이다.

## 구현과 TDD

실패 → 최소 구현 → 통과를 확인한 동작(`tests/test_extract.py`·`tests/test_parse_cli.py`):

- 근거가 한 건뿐이라 코드가 남긴 묶음도 사람이 `같은 지출`로 확정하면 합치고, 합친 레코드의
  `repeats`가 겹친 원본을 가리킨다.
- `별개 지출` 확정은 그 묶음을 남기고, 그 지출을 그 원본 쌍의 재게시 근거에서도 뺀다. 함께 실은
  지출 둘 중 하나가 별개로 확정되면 남은 근거가 한 건뿐이라 나머지도 합치지 않는다.
- 확정이 센 수는 **기준보다 더 합친 만큼**이다. 기준이 이미 합친 원본이 섞인 묶음에서 확정이 원본
  하나를 더 이으면 `confirmed_records`는 1이고 나머지는 `merged_records`에 남는다.
- 장부에 없는 묶음을 가리키는 확정과 한 묶음의 확정 둘은 거부한다.
- 공개 CLI에서 `data/manual/<city>/repeats.jsonl`을 읽어 장부·`records.csv`·`parse.json` 집계가
  함께 움직인다. 다른 도시의 줄은 거부하고, `--org` 실행은 다른 기관의 줄을 보지 않는다.

검사는 `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`, `uv run pytest`
(444건), `git diff --check`를 통과했다.

## 남은 제한

- **값이 달라진 정정본은 이 입력이 다루지 못한다.** 정정본이 금액·날짜·상호를 고치면 동일성 키가
  갈려 두 묶음이 되고, 한 줄이 지출 하나를 가리키므로 그 둘을 묶을 자리가 없다. 광주에는 아직 실제
  사례가 없다 — 콘텐츠산업과 `2월`(12건)과 `…(수정)`(13건)은 값이 같은 12건으로 합쳐졌고 남은
  1건은 정정본에만 있는 새 지출이다. 사례가 나오면 그때 모양을 정한다(ADR-0006).
- 확정한 사실은 레코드에 남지 않는다. 어느 묶음을 사람이 확정했는지는 `repeats.jsonl`과
  `parse.json`의 집계로만 되짚는다. 레코드에 확정 표시를 둘지는 결정하지 않았다.
- `parse`는 이 입력의 해시를 산출물 의존성에 담지 않는다. 입력을 고치면 `parse`부터 다시 돌려야
  하며, 그것은 원본이나 헤더 매핑을 고쳤을 때와 같다.
- 이번 재생성은 PDF 3개와 미해결 원본 16개의 사람 최종 확인을 다루지 않는다. 둘은
  [#66](https://github.com/snowjaewon/OfficialDeliciousMap/issues/66)의 몫이며 그 실행에서 장부가
  한 번 더 움직인다.
