# Issue #154 검증 — 중랑구 게시판 목록 재개

## 원인

중랑구 목록은 853쪽을 순서대로 요청한다. 기존 구현은 한 쪽 요청이 `service-unavailable`로
끊기면 그 실행에서 읽은 목록 색인만 남기고, 다음 실행을 다시 1쪽부터 시작했다. 따라서
전역 재시도(4회)를 모두 소진한 뒤에도 앞쪽 요청을 반복했고, 중단된 실행의
`uncollected_postings` 누계를 복원할 근거가 없었다.

## 선택한 방법

페이지 단위 체크포인트를 목록 스크래퍼에 추가했다.

- 한 쪽의 모든 게시글을 호출자가 소비한 뒤 `listing-progress.json`에 다음 쪽, 목록 주소,
  조회 조건, 누적 필터 수를 기록한다.
- 목록 요청이나 첨부 처리 중 장애가 나면 체크포인트가 아직 현재 쪽을 가리키므로 그 쪽을
  다시 시도한다. 게시글 장부(`collected.jsonl`)는 게시글 단위로 멱등적이다.
- 마지막 쪽까지 끝내면 체크포인트를 삭제한다. 재개 실행의 `uncollected_postings`는
  중단 중에도 보존한 `listing.jsonl` 전체에서 다시 세므로 실행마다 단위가 달라지지 않는다.
- 기존 `postings(skipped)` 호출 계약은 바꾸지 않았다. 체크포인트를 지원하지 않는 합성·기존
  스크래퍼는 이전 동작을 유지한다.

재시도 횟수·백오프·호스트 간격은 변경하지 않았다. 이슈 본문의 실측에서 목록만 훑은 실행이
재시도 4회로 853쪽을 완주했지만 원본 동시 수집은 완주하지 못했으므로, 이번 수정은 느린
간격을 효과가 있는 것처럼 선언하지 않고 실패 지점을 재개하는 데만 초점을 둔다.

## 자동 검증

합성 중랑구 목록에서 1쪽을 끝낸 뒤 2쪽 요청을 실패시키고, 새 실행이 `next_page=2`만
요청하는지와 완주 뒤 체크포인트 삭제를 고정했다.

```text
.venv\Scripts\python.exe -m pytest --basetemp ".tools\pytest-tmp\issue154" tests/test_seoul.py tests/test_collection.py
30 passed
```

실제 853쪽 재수집과 2026년 상반기 원본 장부 재생성은 이 검증에 포함하지 않았다. 원본은
저장소 밖에 있어 해당 환경에서 다시 실행할 때 `fetch.json`의 `collection failures`가
사라졌는지와 `uncollected_postings`를 장부 단위로 확인해야 한다.
