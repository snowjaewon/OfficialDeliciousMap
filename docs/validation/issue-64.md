# 이슈 #64 주소 근거 없는 레코드의 확정 마커 검증 기록

2026-09-12, Windows 11 · Git Bash · Python 3.12.10. 도시는 광주, 기관은 광주광역시청 하나다.
범위는 [주소 근거가 없는 레코드로 확정 마커 만들기(마커 0 해소) #64](https://github.com/snowjaewon/OfficialDeliciousMap/issues/64)다.

## 정한 경로

세 후보 중 **방문 상위 상호부터의 사람 확인**을 택했다. 나머지 둘은 이렇게 판단했다.

- **인허가 자료 대조** — 이번에 쓸 수 없었다. `DATA_GO_KR_KEY`가 없어 조회 자체가 구성되지
  않았고, 후보는 전부 네이버 지역검색에서만 왔다. 독립 제공자가 하나뿐이면 `matched` 자동
  채택의 전제인 "서로 다른 제공자의 근거가 겹친다"가 성립하지 않는다. 키가 준비되면 이 경로가
  확정 건수를 가장 크게 늘릴 수 있다. 후속 작업이다.
- **상호 + 도시 경계 안 지역검색** — 택하지 않았다.
  [지오코딩 계약](../geocoding.md#제공자-조회)은 "요청 맥락의 도시·기관은 질의에 넣지 않는다,
  기관 도시 밖 후보를 거르지 않는다"를 명시한다. 경계로 후보를 거르면 기관 도시 안의 동명이
  업소를 정답으로 밀어 올리게 되어, 바꾸려면 근거를 들어 따로 제안해야 한다.

### 확인 한 줄이 상호 범위에 걸리게 했다

`IdentityConfirmation.scope`는 레코드·원본까지 필수인 `EvidenceScope`였다. 상호 하나를
확인하려면 레코드 수만큼(하해가는 55줄) 같은 근거를 되풀이해 적어야 했다. 상호 복원이 이미
쓰던 범위 계약을 `ReviewScope`로 고쳐 함께 쓰게 했다. `city`와 원본 표기 `merchant`는 필수,
`organization`·`source_hash`·`record_id`는 범위를 좁히는 선택 항목이다. 좁은 줄이 넓은 줄을
대신하는 규칙과 충돌 판정도 상호 복원과 같고, 규칙은 `restoration`이 한 벌만 소유한다.
레코드마다 적용한 결과는 새 `ConfirmedPlace`로 `GeocodeResult.confirmation`에 그대로 남는다.
적용이 좌표 판정의 일부이므로 `identity.POLICY_VERSION`을 `identity-2`로 올렸고 geocode
산출물은 envelope v5가 됐다.

## 확인 기준

원본에는 상호밖에 없다. 그래서 확인은 아래를 **모두** 만족할 때만 했다. 판단은 손으로 고른
목록이 아니라 기준 그대로 기계적으로 적용했다.

1. 방문 **11회 이상**인 미확정 상호다. 10회에는 동률 상호가 여럿이라 거기서 끊었다.
2. 원본 표기와 **공백을 무시하고 정확히 일치**하는 후보가 조회 결과에 **딱 하나**다.
   후보의 상호와 지점을 이어 붙인 표기가 원본과 같은 경우도 정확 일치로 봤다(`규슈 상무점`).
3. 그 후보의 주소가 **기관 청사와 같은 상무지구**다. 판단은 도로명으로 한다 — 내방로·천변좌하로·
   치평로·시청로·시청서편로·상무중앙로·상무번영로·상무시민로·운천로. 청사 주소는 기관이
   스스로 밝힌 `전남광주통합특별시 서구 내방로 111(치평동)`이다([#51 실측](issue-51.md)).

3번은 처음에 "관할 도시 안이면 되고, 청사 생활권 밖이면 원본 표기로 시작하는 다른 후보가 청사
근처에 없을 것"으로 잡았다가 좁혔다. **그 형태는 부재 증명이었다.** 후보 5건 안에 없다는 것뿐이고,
같은 이유로 보류한 `목사골`과도 규칙이 어긋났다. 지금 기준에는 부재 증명이 없다.

### 이 근거의 무게

**지점·주소의 독립 근거는 없다.** 원본에 주소 열이 없으므로 확정한 12건 모두 후보 자신이 준
주소를 그대로 확인한 것이고, 뒷받침하는 것은 상호 표기의 정확 일치와 기관 소재지 맥락뿐이다.
[#33 확정 정책](https://github.com/snowjaewon/OfficialDeliciousMap/issues/33#issuecomment-5615154736)이
요구하는 독립 근거는 `matched` 자동 채택의 조건이고, 이 12건은 그 경로가 아니라 사람 확인
경로로 들어왔다. 사람 확인이 독립 근거 요건을 면제하는 것은 아니므로 각 줄의 `evidence`에
이 한계를 그대로 적었다. 틀린 것이 드러나면 그 줄을 고치거나 지우면 판정이 되돌아간다.

**확인은 에이전트가 했고 사람의 최종 확인은 이 PR 검토다**(2026-09-12 사용자 결정).
계약에도 이 경로를 적었다(`docs/geocoding.md` 사람 확인 절, `IdentityConfirmation` docstring).

## 실행과 결과

이 브랜치는 [#61](https://github.com/snowjaewon/OfficialDeliciousMap/issues/61)·#62·#63이
머지된 `develop`(`f715dd7`) 위에 있다. 그 시점의 커밋된 광주 산출물은 `parse` v2로 낡아
있었으므로([#63 검증](issue-63.md)의 "커밋하지 않은 것"), **`parse`부터 다시 돌렸다.**
그래서 이 변경은 #62·#63이 남겨 둔 재생성도 함께 반영한다.

저장소 루트, Git Bash.

```text
uv run --env-file .env python -m deliciousmap parse --city gwangju
uv run --env-file .env python -m deliciousmap classify --city gwangju
uv run --env-file .env python -m deliciousmap geocode --city gwangju
uv run --env-file .env python -m deliciousmap closure --city gwangju
uv run --env-file .env python -m deliciousmap build --city gwangju
```

이 세션에는 `.env`가 없어 같은 다섯 단계를 `cli.main`에 **요청이 오면 실패하는 transport**를
넣어 실행했다. `build`의 공개 지도 키는 자리표시자를 넣었고 그 값은 `dist/`에만 들어간다.
`dist/`는 커밋하지 않는다.

**새 외부 호출은 한 건도 없다.** `geocode-lookup-v1.jsonl`(1,252,591바이트 · 1,069줄),
`headermap-answers-v1.jsonl`, `data/_shared/`의 서명 캐시·판별 캐시·LLM 예산 장부가 모두
바이트 그대로다. 캐시에 없는 조회가 하나라도 있었으면 `lookup_error`와 종료 1이 났다.

## 테스트

- `test_merchant_scoped_confirmation_maps_every_record_without_address_evidence`
  — 주소 근거가 없어 `missing_address`로 남던 레코드들이 상호 범위 확인 한 줄로 모두
  `human_confirmed`가 되고 방문 2회의 마커 하나가 된다.
- `test_confirmations_disagreeing_on_the_place_are_reported_not_chosen`
  — 같은 업소를 가리키면 좁은 줄의 근거를 남기고, 다른 업소를 가리키거나 어느 쪽도 좁지 않으면
  종료 1로 알린다.
- 기존 확인 테스트(제공자 좌표 충돌, 복원명 충돌, 좌표 출처 표시)는 범위에 원본 표기를 더한 것
  말고는 그대로 통과한다.
