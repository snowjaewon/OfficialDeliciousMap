# 이슈 #61 판정 이력 키·분할 검증 기록

2026-09-12, Windows 11 · Git Bash · Python 3.12.10. 도시는 광주, 기관은 광주광역시청 하나다.
범위는 [#59 검증](issue-59.md)의 "찾은 것"이 남긴 두 갈래, 곧 판정 이력이 상류 변경마다 통째로
늘어나는 것과 20MB 상한이다. 결정은 [ADR-0003](../adr/0003-narrow-geocode-history-key.md)에 있다.

## 이슈 서술의 정정 두 가지

**하나. 상한 검사는 있었다.** 이슈와 #59 검증은 "`append_cache_entries`가 `require_size`를 부르지
않아 이 이력은 조용히 넘는다"고 적었다. 사실이 아니다. `append_cache_entries`는 `write_text`로
쓰고, HEAD(`21cce87`)의 `write_text` 첫 줄이 `require_size(content)`다. 상한을 넘으면 조용히
넘어가는 것이 아니라 `artifact exceeds 20MB; partition before writing`으로 **geocode 단계 전체가
실패**했을 것이다. 실제 문제는 "검사가 없다"가 아니라 "넘길 때 나눌 방법이 없다"였다.

**둘. 여유는 5.24MB가 아니라 4,522,907바이트였다.** 이슈는 14.76MiB로 잰 파일 크기를 20MB 상한과
섞어 비교했다. 상한은 20,000,000바이트(십진)다.

| 값 | 바이트 |
| --- | --- |
| HEAD의 `geocode-history-v2.jsonl` | 15,477,093 (14.76MiB) |
| 상한까지 남은 여유 | **4,522,907** |
| 이번 키 변경이 더한 줄 2,325개 | **5,159,031** |

곧 고치지 않았다면 같은 성격의 상류 변경 **한 번**에 상한을 넘어 geocode가 실패했을 것이다.
"사실상 상한에 닿는다"가 아니라 이미 다음 한 번에서 넘는 상태였다.

## 고친 것

- `lookup_key`에서 선행 산출물·후보 파일·조회 캐시·검토 파일의 **파일 해시를 뺐다**. 남은 것은 그
  레코드의 값, 그 레코드에 적용한 조회 결과, 그 레코드의 사람 확인·확정 복원명, 판정 정책 키다.
  판정이 그 파일들에서 실제로 읽는 값은 이미 키 안에 값으로 들어 있다.
- 산출물 단위의 낡음을 보는 envelope의 `dependencies`는 **그대로 두었다**. 아래 실측에서 옛 판과
  새 판의 `dependencies` 키 9개가 같다.
- 추가형 이력에 분할을 넣었다. 이번 배치가 마지막 조각에 들어가지 않으면 그 조각을 그대로 닫고
  `<이름>.002.<확장자>`부터 다음 조각을 연다. 읽는 쪽은 번호 순으로 이어 읽고, 번호가 비었거나
  같은 `(key, revision)`이 두 조각에 있으면 실패한다. 여러 조각을 열 때는 쓰기 전에 모두 만들어
  크기를 확인하므로 일부만 써 두고 실패하지 않는다.
- 조각이 늘면 줄 순서와 revision 순서가 어긋날 수 있다. "유효한 최신 판정"을 줄 순서가 아니라
  `valid=true`인 가장 큰 revision으로 고르게 했다(`storage.latest_valid`·`highest_revision`,
  `select_cache`·`previous_geocodes`·`classify`·`headermap`). README가 적어 온 규칙 그대로이며,
  이제 구현이 파일 배치에 기대지 않는다.
- 지나는 길에 `docs/geocoding.md`의 "build는 ... v5다"를 **v6**으로 고쳤다. `SCHEMA_VERSIONS`와
  커밋된 `build.json`이 모두 6이므로 문서만 뒤처져 있었다.

## 실측 — 광주광역시청 재생성

`.env`의 네이버 검색 키만 넣고 `geocode` → `closure` → `build`를 다시 돌렸다. 실행 중 소켓 연결을
막아 두었고 **외부 호출은 0회**다. 커밋된 `geocode-lookup-v1.jsonl`이 조회 2,325건을 모두 덮는다
(캐시 항목 1,069개, 실패 조회 0건).

| 파일 | 전 | 후 |
| --- | --- | --- |
| `geocode-history-v2.jsonl` | 15,477,093바이트 · 6,975줄 | **바이트 그대로** · 6,975줄 |
| `geocode-history-v2.002.jsonl` | 없음 | **5,159,031바이트 · 2,325줄** |
| 이력 합계 | 15,477,093바이트 · 6,975줄 | 20,636,124바이트 · 9,300줄 |
| `geocode.json` | 4,772,037바이트 | 4,772,037바이트 |

두 조각 모두 상한 아래다(15.48MB · 5.16MB). 한 파일이었다면 20,636,124바이트로 상한을 넘어
쓰기가 실패한다. 키 식이 바뀌었으므로 이번 한 번은 2,325건이 새 키로 다시 쌓인다.

조각 1에는 **4,522,907바이트가 남은 채로 닫혔다**. 이번 배치(5,159,031바이트)가 통째로 들어가지
않았기 때문이다. 조각을 꽉 채우려면 조각 1까지 다시 정렬해 써야 하는데, 이슈가 "커밋된 이력을
다시 쓰지 않는 방법을 고른다"고 정했으므로 그렇게 하지 않았다. 15MB 파일을 다시 쓰면 git 이력에
15MB가 더 쌓이며, 그것이 ADR-0001이 막으려는 비용이다.

**판정은 하나도 바뀌지 않았다.** `lookup_key`·`dependency_key` 두 칸을 뺀 결과 2,325건이 옛 판과
값까지 같다. `status`는 전부 `failed`이고 `reason`은 `missing_address` 2,055 · `no_candidates` 270,
마커는 0으로 전과 같다. `closure.json`·`build.json`은 `geocode.json` 해시만 바뀌고 payload는 같다
(레코드 2,921 · 마커 0).

`dependency_key`는 이제 실행 전체에서 값 하나(정책 키)이고 `lookup_key`는 2,325건이 모두 다르다.
같은 이름의 다른 업소로 캐시가 번지는 것은 여전히 막힌다.

### 변경 없는 재실행

같은 명령을 한 번 더 돌렸다. 두 조각 모두 **MD5까지 같다**. 이력에 줄이 늘지 않는다.

### 상류 메타데이터만 바뀐 재실행 (#59 상황 재현)

커밋된 `data/`를 복사한 뒤 `parse.json`의 `reporting_period`만 바꾸고(레코드·분류는 그대로),
`classify.json`의 `parse.json` 해시를 맞춰 두고 geocode를 다시 돌렸다. #59에서 집계 세 칸을 더한
것과 같은 성격의 변경이다.

| 항목 | 결과 |
| --- | --- |
| 종료 코드 | 0 |
| `geocode-history-v2.jsonl` | 15,477,093바이트 · 6,975줄 → **그대로** |
| `geocode-history-v2.002.jsonl` | 5,159,031바이트 · 2,325줄 → **그대로** |
| 더해진 줄 | **0** |
| `geocode.json` payload | 재생성 판과 **동일** |
| envelope `dependencies` | `parse.json`·`classify.json` 두 칸만 새 해시 |

HEAD의 키 식이었다면 여기서 2,325줄(5,159,031바이트)이 더 쌓였을 것이다. 나눌 방법이 없었으므로
한 파일이 25,795,155바이트가 되어 `require_size`에 걸리고 geocode 단계가 실패했을 것이다.

산출물 단위의 낡음 검사는 좁히지 않았으므로 `geocode.json`은 이번에도 다시 써야 했고, 그 결과
envelope의 두 칸이 새 해시가 되었다. 달라진 것은 **이력에 줄이 늘지 않는다**는 점뿐이다.

## 남은 제한

- 판정은 전부 미확정이다. 확정 업소 0건·마커 0건이라 좌표를 쓰는 경로는 이 실행이 확인하지 못했다.
- `reconcile_coordinates`는 여러 레코드를 함께 보는 유일한 규칙이다. 같은 업소의 좌표 충돌로 보류된
  판정은 상대 레코드만 바뀌어 충돌이 풀려도 이 레코드의 키가 그대로라 보류가 남는다. 지금 확정
  업소가 0건이라 해당 사례가 없고, 판정 규칙은 이 이슈의 범위 밖이다. 후속으로 다룬다.
- 이력이 20.6MB가 되어 `read_cache`가 매 실행 두 조각을 모두 읽는다. geocode 한 번이 약 3분
  걸린다. 성능은 [#29](https://github.com/snowjaewon/OfficialDeliciousMap/issues/29)의 범위다.
- 조각 번호는 999까지다. 그 앞에서 담당자가 범위를 나눠야 한다.
- 이미 쌓인 6,975줄은 그대로 둔다. 되돌리면 이전 `geocode.json`의 `lookup_key`와 어긋난다.
- 마지막 조각은 append마다 통째로 다시 쓴다. 앞 조각은 다시 쓰지 않지만, 마지막 조각의 diff는
  그 조각이 찰 때까지 계속 커진다. 대가는 ADR-0003에 적었다.
- `GeocodeResult.dependency_key`는 이제 이름이 내용과 어긋난다(담기는 것은 판정 정책 버전이다).
  계약이 `extra="forbid"`라 이름을 바꾸면 이미 쌓인 6,975줄을 읽지 못하므로 두었다. 이름을
  고치려면 이력 파일을 v3으로 돌리는 별도 결정이 필요하다.
