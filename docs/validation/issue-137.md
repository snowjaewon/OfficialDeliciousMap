# 비식당 판별도 꼬리말을 뗀 이름을 읽는다 (#137)

2026-09-14 실행. [#127](issue-127.md)이 조회와 좌표 판정에서만 뗀 이름 없는 동행 업소의
꼬리말을 **비식당 판별(`classify`)에서도** 떼고 광주를 다시 돌린 기록이다. 비교의 기준점은
`origin/develop` db8a578이며 수치는 커밋된 산출물에서 다시 셀 수 있다.

**레코드의 원본 표기는 어느 단계에서도 바뀌지 않는다.** 바뀐 것은 판별기에 보이는 이름과
공통 캐시를 찾는 키뿐이다.

## 1. 판별이 읽는 이름을 고르는 순서

규칙은 `merchants.chosen_name` 하나다.

| 순서 | 이름 | 예 |
| --- | --- | --- |
| 1 | 확정 복원명 | `합성카페외 1` + 복원 `합성카페 본점` → `합성카페 본점` |
| 2 | 꼬리말을 뗀 이름 | `카페말바우외 1` → `카페말바우` |
| 3 | 원본 표기 | `외갓집`·`외 1` → 그대로 |

세 자리가 그 함수 하나를 부른다 — 조회(`lookup.resolve`), 좌표 판정(`identity.decide_identity`),
그리고 이번에 더한 판별(`ClassifyInput.names`)이다. 꼬리말을 읽는 정규식은 `merchants.read`가
그대로 소유하며 새 정규식이나 둘째 규칙을 만들지 않았다.

classify 단계는 `ClassifyInput.names()`가 준 이름으로 캐시를 채우고 같은 이름으로 판정을 읽는다.
캐시를 채우는 키와 판정을 읽는 키가 한 자리에서 나온다.

떼면 이름이 하나도 남지 않는 표기(`외 1`)와 이름 가운데의 `외`(`외갓집`)는 원본 표기 그대로
판별한다. 조회할 이름을 지어내지 않는다. 이 선택은 `tests/test_classify_cli.py`와
`tests/test_merchants.py`가 행동 테스트로 막았다.

## 5. 사람 보정이 뗀 이름에도 맞는다

2026-09-14 사용자 결정으로 사람 보정도 뗀 이름으로 맞춘다. 판별이 보는 이름이 하나로 일관되게
유지되는 쪽을 골랐다.

그 결과 **`목사골농장 외 1` 2건**(`089bf5b7aef667d4-sheet2-R19`·`-R42`, gwangju-city)이
[#122](issue-122.md)의 사람 보정(`목사골농장`, `restaurant`)에 새로 걸려 판단 보류에서
식당으로 갈렸다.

**이 2건은 #122를 쓴 사람이 글로 뺀 표기다.** 그 근거 줄은 적용 범위를 네 줄로 밝히며
*"`목사골농장 외 1`과 법인명 `주식회사 목사골`, 여러 상호를 함께 적은 칸은 넣지 않았다"*고
적었다. 규칙을 일관되게 둔 결과 그 사람이 명시적으로 뺀 표기가 범위에 들어왔으므로, 이 2건은
**#122의 사람이 승인해야 하는 범위 확대**다. PR 본문에 수와 상호를 밝히고 검토를 청한다.

사람 보정이 맞은 상호는 캐시를 채우지 않으므로 이 2건은 LLM 호출을 일으키지 않았다.

## 8. 검증 명령

저장소 루트에서 Git Bash·PowerShell 공통.

```text
uv run --env-file .env python -m deliciousmap classify --city gwangju
uv run --env-file .env python -m deliciousmap geocode  --city gwangju
uv run --env-file .env python -m deliciousmap closure  --city gwangju
uv run --env-file .env python -m deliciousmap build    --city gwangju
uv run pytest
uv run ruff check .
uv run ruff format --check .
node --test tests/site_behavior.test.js tests/measure_map.test.js tests/service_worker.test.js
git diff --check
```

`.env`를 싣지 않으면 `classify`가 모델을 구성하지 못해 **모든 상호가
`unclassified: model_not_configured`로 떨어진다.** 그 실행은 이 측정이 아니다(4절이 그 밀린
상태를 정리한 기록이다).

pytest 652건 + node 92건이 통과했고 Ruff lint·format이 통과했다.

## 9. 남긴 구멍 — `classify`의 낡음 판정이 꼬리말 규칙을 모른다

`storage._dependencies`는 `merchants.POLICY_VERSION`을 `parse`와 `geocode`에만 넣는다. 이번
변경으로 **`classify`도 그 규칙을 읽게 됐는데 그 낡음 판정은 여전히 모른다.** 꼬리말 정규식이
언제든 바뀌면 `Store.load("classify", …)`가 옛 규칙으로 계산한 판정을 신선한 것으로 통과시킨다.

이미 그런 산출물이 있다. `data/ulsan/classify.json`은 옛 규칙으로 계산됐고 울산 레코드 124건
가운데 **11건이 꼬리말**인데 아무것도 그 사실을 알리지 않는다.

**이 PR에서 고치지 않았다. 2026-09-14 사용자 결정이다.** `classify`를 그 집합에 넣어 보면
`build --city gwangju`와 `build --city ulsan`이 둘 다 `invalid-artifact`로 끝난다(직접 실행해
확인했다). 광주는 classify 재실행이 캐시 적중이라 LLM 0회지만, 울산은 뗀 이름 기준 캐시에 없는
이름이 86개(약 3요청 · USD 0.03)이고 현재 판정 124건 가운데 110건이 `unclassified`라 재실행하면
울산 데이터가 크게 바뀐다. 그것은 #137이 out of scope로 둔 다른 도시이며
[#132](issue-132.md)의 담당 영역이다. 그래서 이 구멍은
[#147](https://github.com/snowjaewon/OfficialDeliciousMap/issues/147)로 남긴다.

## 10. 하지 않은 것

- **`classify`의 낡음 판정은 고치지 않았다.** 위 9절과 [#147](https://github.com/snowjaewon/OfficialDeliciousMap/issues/147)이다.
- **좌표 확정은 0건이다.** 식당으로 갈린 24건은 후보를 얻어 [#135](https://github.com/snowjaewon/OfficialDeliciousMap/issues/135)의 사람 확인 대상이 됐을 뿐이다.
- **꼬리말 규칙 자체는 건드리지 않았다.** 새 꼬리말 형태를 더하지 않았고 `merchants.read`의
  정규식은 그대로다.
- **광주 외 도시는 세지 않았다.** 다른 도시의 꼬리말 수는 실측하지 않았다.
- **합쳐 적은 상호는 그대로다.** 쉼표·슬래시·`&`·`및`로 둘을 다 적은 표기는
  [#117](https://github.com/snowjaewon/OfficialDeliciousMap/issues/117)·[#128](https://github.com/snowjaewon/OfficialDeliciousMap/issues/128) 범위다.
- **잘린 상호 복원은 그대로다.** 꼬리말을 떼도 후보가 0건인 것은
  [#136](https://github.com/snowjaewon/OfficialDeliciousMap/issues/136) 범위다.
- **기관별 작업 산출물(`data/gwangju/orgs/*`)은 다시 돌리지 않았다.** 배포되는 것은 6개 기관
  레코드를 모두 담은 도시 실행이다. [#127](issue-127.md)의 같은 제한이 그대로 남는다.
- **업소별 금액은 가르지 않았다.** [ADR-0007](../adr/0007-do-not-split-unallocated-amounts.md)이
  금지한다.
