# AI는 헤더를 매핑하고 코드는 레코드를 추출한다

[스펙 지도 #1](https://github.com/snowjaewon/OfficialDeliciousMap/issues/1)의 AI 사용 경계를 구체화한다. 원본의 비어 있지 않은 상위 12행으로 LLM이 헤더 매핑을 판정하고, 전체 레코드 추출과 검증은 코드가 담당한다. 전량 추출은 코드 검증 실패를 헤더 매핑 재호출로도 해결하지 못할 때만 사용하는 폴백으로 제한한다. 이 결정은 2026-09-10 사용자가 [#18](https://github.com/snowjaewon/OfficialDeliciousMap/issues/18)의 정책과 함께 확정했다. 실제 파이프라인 구현은 후속 작업이다.

[프로토타입 #10](https://github.com/snowjaewon/OfficialDeliciousMap/issues/10#issuecomment-5602701646)에서 격자로 읽은 원본 83개 중 80개는 모든 평가 항목이 정확했고, 나머지 3개는 부서 정답 라벨이 모호했다. 전량 추출이 필요했던 표본은 0개였다. HWP 3개와 HWPX 2개는 파서가 없어 평가에서 빠졌으므로, 이 결과를 해당 형식이나 전체 원본의 성공률로 일반화하지 않는다.

## Considered Options

- **형식별 코드만 사용**: 비용은 적지만 기관별 열 이름·헤더 위치·금액 단위를 계속 수작업으로 유지해야 한다.
- **LLM으로 항상 전량 추출**: 행 수에 비례해 호출량과 생성 오류 검증 부담이 늘어난다. 표본에서는 전량 추출 없이 헤더 매핑으로 처리할 수 있었다.
- **헤더 매핑 + 코드 추출 + 제한된 폴백(채택)**: 반복되는 양식은 캐시로 재사용하고, 레코드 생성은 재현 가능한 코드에 둔다. 대신 격자 변환과 카드형 등 별도 파서는 여전히 필요하다.

## Consequences

- 여러 표가 있는 원본은 독립된 표마다 비어 있지 않은 상위 12행을 입력으로 삼는다. 제목·연도·단위 등 해당 표에 적용되는 문서 맥락은 출처 위치와 함께 전달한다. 표 경계를 확인하지 못하면 검증 실패로 처리한다.
- 헤더 매핑 스키마는 `layout`(`table` / `key_value` / `none`), `header_rows`, `data_start_row`, `year_hint`, 열 역할과 금액 단위를 포함한다. 역할은 집행일·상호·목적·부서·금액 및 분리된 `month` / `day` / `time`을 표현한다. 프로토타입의 스키마를 출발점으로 삼되 정식 코드와 데이터는 별도로 구현한다.
- 캐시 서명은 정규화한 헤더 텍스트와 열 수에 기반한다. 캐시 적중도 코드 검증을 생략하는 근거가 아니다. 헤더 없는 표에는 공통 헤더 서명 캐시를 쓰지 않는다.
- 검증 실패 시 해당 원본에서 캐시 재사용을 중단하고 재호출한다. [ADR-0001](0001-commit-refined-artifacts.md)의 추가만 하는 캐시 정책에 맞게 기존 항목은 삭제하지 않고, 실패 근거와 검증된 새 판정을 추적한다. 캐시 버전과 판정 선택 방법은 후속 구현에서 정한다.
- 카드형은 별도 코드 파서로 처리한다. PDF 숫자 분리·엑셀 날짜 시리얼·셀 안 반복 라벨도 코드 추출의 책임이다. 모델 호출은 개발자 PC의 수집·파싱 시점에만 하고 배포 사이트에서는 하지 않는다.
- 조정 가능한 통과율·호출 상한·대조 절차는 [폴백 정책](../specs/header-mapping-fallback.md)에 분리한다. 원본 외부 보관과 정제 산출물 커밋 정책은 ADR-0001을 유지한다.
